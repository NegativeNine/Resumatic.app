# Job seeker threat model

Scope: accounts with Google sign-in, career uploads and facts, generated outputs, billing, coach snapshots, connected MCP apps, erasure and administrative recovery. This is a repository threat model and test plan; an independent security assessment remains a release requirement.

## Assets and trust boundaries

Career text and original uploads are private to one Vault. The Worker authenticates users and validates requests; the Vault independently checks ownership, session generation, security epoch and open state. The Directory is an identity and administration control plane and is not called by `/api/*` data requests. Model responses, uploaded documents, job descriptions, OAuth client metadata, browser-submitted selections and any page the posting reader fetches are untrusted inputs.

Model prompts and outputs may cross the configured model-provider boundary. OAuth KV contains encrypted authorization props, client records and bearer-token records; the Vault contains the authoritative local permissions. Stripe holds payment information. Browser Run receives escaped rendering data. Analytics and alert receivers receive metadata only.

## Coach and connected-app limits

A coach grant shares a fixed selection for at most seven days, with at most 100 facts, 20 resume versions, 20 documents and one MiB of copied content. Contact fields already printed on a selected resume are included. A recipient can copy what they can read; revocation ends future server access and cannot erase the recipient's copies. Coach access has no write path and never gains access to subsequently created content.

A copy can also carry its owner's name and, beside each resume, the title and company of the job it was tailored for. Both are off unless the owner turns them on for that copy, because a copy of facts alone names nobody and where someone is applying is theirs to tell. They are fixed when the copy is made, as the rest is. The label an owner gives a link (who it is for) is kept with the grant for the owner's list and export, and is never sent to the reader.

A copy can hold cover letters and interview preparation, as their words only. One is shared only if every sentence still passes the deterministic checks (numbers, names, scope, and that a sentence under a role cites only that role's facts) against the full fact records captured when it was written. That is the gate a resume passes before it is exported or shared, and it runs again on every read against the saved document, which must come out exactly as the copy holds it. A document written before those records were kept has nothing to be checked against and cannot be shared; the owner writes it again. Interview preparation carries its questions, which are built from the posting's requirements. The posting, the facts cited and their quotes are not shared. A copy that holds documents is schema version 3, so code from before documents could be shared refuses it instead of serving a part it never checked.

The Vault records when a copy was last read, to the minute, and the owner's list shows that time. It records nothing about the reader: no address, browser or count. The copy tells its reader that the owner can see when it was last opened. Checking whether a link still works, as the owner's list does, is not recorded as a read, and neither is the owner opening their own copy in a browser where they are signed in. An owner who opens it anywhere else is recorded like any reader.

A copy can name one coach by the address they sign in with. Naming a coach never widens who can read: anyone with the link still reads the copy, and the named account gains only a way back to the same copy without the link. The address reaches the Worker in the reader's own session token, which carries it from the provider-verified sign-in (signed, not encrypted: it is the holder's own address, in their own HttpOnly cookie). It is the address as of that sign-in, so a change of address at the provider takes effect at the next sign-in, within the seven days a session lasts. A session from before the address was carried is nobody's coach until its holder signs in again. When the named account takes the copy up, the owner's Vault keeps that account's ID, the name on it and the time, and the owner sees the name and time; these go when the link expires. Taking the copy off the coach's list changes none of that, and while the link lasts the same account can add the copy again. What the copy tells that account, that it is in their client list or that it can be added, takes both Vaults: the owner's says the account took the copy up, and the account's own says whether its list holds it. When the account's own Vault can't be asked, as with a session that has since been signed out, the owner's Vault's word stands. A list with no room refuses a copy before its owner's Vault is told of a take-up. The coach's Vault keeps the copy's ID, where it is kept, the owner's name as the copy gives it, and the copy's last day. An entry is unseen and cleared thirty days after that last day, and its owner can end access at any moment before. Taking a copy up sets the coach's Vault's alarm for the time its entry is due to be cleared, and the alarm is set again for the next entry whatever it fired for, so an entry is cleared even in an account that does nothing but coach. The list is in the coach's export without where each copy is kept, is deleted with the account, and moves with the Vault to a replacement: it holds no credential, and the copy's owner's Vault decides every open as before. A Vault fenced for maintenance clears nothing from the list until the fence is lifted. Coach accounts are ordinary accounts: nothing here creates one, invites one or bypasses the invitation gate.

The grant ID appears in the reader's address bar after the exchange (`/share?g=…`) so a reload opens the same copy. It is an identifier, not a credential: reading a copy needs that copy's HttpOnly cookie, which lasts at most an hour. The cookie used before copies had their own is still set and still read when a request names no copy, so a page loaded before this change keeps working.

MCP read access exposes confirmed facts and finished resumes, not original files, evidence quotes or private application notes. Generation permission is separately selected and uses the same quota as the web application. The jobs permission is selected separately too: it lists saved jobs (title, company, the start of the posting, link, status and each resume's ID, never notes or the whole posting) and adds a job from its description. A posting a connected app supplies is untrusted input, as a pasted one is. Access without offline permission lasts at most one hour; approved offline access lasts at most thirty days. Every consent is explicit; remembered or silent consent is disabled. A reauthorization creates its own local grant and does not silently extend another grant.

Job preferences are in neither a copy nor any tool's answer.

OAuth KV remains eventually consistent. The local gate establishes immediate application revocation; remote credentials are subsequently removed with retryable cleanup. Deletion audit counts both grant and token keys, including orphan tokens. OAuth client registration records are shared application metadata and are not deleted merely because one user disconnects that client. Short-lived consent transactions contain the client authorization request, not the user's career content.

## Before public launch

An external tester should exercise Google account-linking/session boundaries, OAuth CSRF and redirect validation, private-network metadata URLs (for OAuth client metadata and, where it is enabled, the posting reader, including public names that resolve inward and redirects that point inward), share links through real browser navigation, upload expansion limits, billing webhook reordering, and deletion/recovery races. Do not call a local stand-in or an unconfigured service a passing external test. Record findings and fixes against the release commit, and require zero open high-severity findings.

Use synthetic identifying canaries to check every enabled log destination. Confirm platform retention for Workflow state, gateway/Worker logs and recovery history after deletion. The script's `retentionReviewed` field is an explicit operator conclusion; zero live-store counters alone do not settle historical retention.
