# Owner-confirmed skill periods

This implements the owner-entry path permitted by the agreed taxonomy pipeline design. It does not decide the broader alternatives in [years-per-skill.md](decisions/years-per-skill.md): parsing explicitly dated source statements, handling undated duration statements, presenting estimates, and recruiter-card bands remain separate decisions and work.

`SKILL_YEARS_ENABLED` must be exactly `true` in both the Worker and Vault before its owner API and UI are offered. It is absent/off by default and production config validation refuses enablement pending staging verification. This change does not turn it on anywhere. No model reads dates or calculates duration.

An owner selects an existing confirmed skill fact, or a confirmed nonshadow exact skill, knowledge, skill-group, tool or tool-category tag on a current confirmed fact or standalone clause/result part. Occupations and mention parts are ineligible. No hierarchy rollup occurs. A tag identifies the chosen concept; the owner's explicit statement establishes the dates of use. A role's dates never supply a skill interval. A fact-backed identity is one exact fact, not all facts whose labels resemble it.

The owner enters a start and end as `YYYY` or `YYYY-MM`, or explicitly chooses ongoing use. No dates are prefilled. Save explicitly confirms use during that period. Editing requires its current revision; withdrawing invalidates dependent totals without erasing owner history. Every mutation has an idempotency key; reusing a key for different input conflicts.

The calculation unions overlaps for the same exact skill key once. It computes guaranteed completed months and possible completed months from uncertain endpoints, excluding the current incomplete UTC month. Year-only endpoints remain uncertain across that whole year. For example, `2020` to `2024` supports 36–60 completed months and prints **“Go — at least 3 years of use, confirmed as of 2026-11”** at that as-of month. `2020-01` to `2021-01` supports 11–13 complete months; no exact days are invented. A mixed-precision union prints in years, rounded down; a month-only union prints in months. Unknown duration and less than one supported output unit produce no claim, never a zero-year claim.

Preview is separate from confirmation. The owner confirms the exact lower-bound wording and its input hash. Claims are immutable; reconfirmation creates a new one. Ongoing use is fixed at the explicit as-of month and never silently grows. A new or edited active interval, a withdrawn period, a changed source identity or decision, and deleted supporting records invalidate prior claims. Privacy is distinct: marking a supporting fact private blocks use without changing the owner's historical claim; unmarking restores use only while all inputs still match. A private interval is never available to a new resume.

New-resume controls offer current public claims with none preselected. Only explicit selections enter that generation snapshot. They have no embedding, relevance score or job-coverage credit and print exactly as confirmed under skills, without a model rewriting their number, skill or date. A derived claim used as a line citation must be the sole citation and retain its entire exact wording. Refinement may retain only claims already explicitly printed in that resume. Changing or withdrawing an input fences later model reservations and current publication. Saved owner history remains readable; invalid/private claims prevent outward resume publication, downloads, shared-copy reads and connected-app resume reads until removed or legitimately current again.

Migration 38 appends `skill_record_identities`, `skill_use_intervals`, `skill_duration_claims`, and `skill_year_requests`. Each claim uses a real internal backing fact to reuse generation snapshot incarnations. These backing rows are read-only through generic fact mutations and absent from generic facts/review/Today, matching, cards, skill lists, fact sharing, connected-app fact search, embedding, and automatic generation selection. Their minimal snapshot proof contains only claim ID, method, input hash, exact text and as-of month; raw period/claim snapshots do not ride shared or connected-app serializers. A resume explicitly containing a claim uses the existing resume-sharing and export consent/projections.

Opaque identity tokens cover supporting facts, roles, splits, parts and tags. Material changes, including change/revert, deletion/recreation, evidence mutation and source-revision mutation, invalidate the old token. These tokens authenticate current owner inputs; they do not turn an upload's mutable quote into historical source proof. Fenced transfer imports source tokens after the underlying records; insertion never manufactures replacement tokens during import, and completion refuses missing identities. Owner JSON/ZIP exports include the four new tables; transfer preserves them and retry receipts; account deletion erases the Vault storage containing them.

The first implementation limits a Vault to 128 historical periods, 256 immutable totals and 5,000 retry receipts; a resume may explicitly select at most 12 totals, one per exact skill. These limits bound claim recalculation on current privacy/publication checks.

Local evidence covers uncertainty/overlap calculations, owner API authorization and concurrency, immutable claims and source change/revert guards, exact number/skill binding, explicit generation, private/withdrawn inputs before model reservations and after saved publication, share/MCP/binary outward gates, generic-projection isolation, transfer and missing identity refusal, migration compatibility, and the owner controls. Real staging browser acceptance, rollout/lifecycle drills and any wider policy decisions remain release evidence to collect before enablement.
