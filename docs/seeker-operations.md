# Job seeker deployment and operations

This runbook covers the Google-only job seeker application. Repository implementation and local tests do not establish that a deployed service, model, payment or deletion audit has passed.

## Configure and provision

Production is the top-level `wrangler.jsonc` configuration. Staging is `env.staging`. Do not deploy production using `--env production`.

```sh
npm ci
npm run typecheck
npm test
node --test scripts/config.test.mjs
npm audit --audit-level=high
node scripts/setup.mjs staging
```

The setup command above prints a local plan. It makes no external request. After reviewing the configured account, bucket and gateway, an operator can use `scripts/setup.sh staging --apply --secrets`. `--apply` creates missing resources and updates the gateway to authenticated access, caching off and logging off. Existing resources are reused. The optional `--secrets` flag requires an interactive terminal and writes Worker secrets; values are never printed by the script. Run the corresponding production command only against the reviewed top-level configuration.

Before a staging deployment or live inference, run `node scripts/check-evaluation-secrets.mjs` with the staging Cloudflare account and a token permitted to list Worker secret names. It returns pending if names cannot be listed or if a secret shadows an evaluated model, extractor, or `ROLE_UNKNOWN_END_ENABLED` variable; it never prints Wrangler output or secret values. CI performs the same check. Never treat a 404, missing Worker, or permission error as an empty list. For first-time bootstrap, `scripts/setup.sh staging --apply --secrets` invokes interactive `wrangler secret put`; the pinned Wrangler version offers to create an inert draft Worker if the Worker does not yet exist. Confirm the intended account and draft creation in the terminal, then rerun the secret-name check before any application deployment or model call. Verify this behavior on the actual account; a failed or ambiguous bootstrap remains pending. Cloudflare documents that [secret changes create Worker versions](https://developers.cloudflare.com/workers/configuration/secrets/).

Set the real Google client, Access team/audience, Cloudflare account and gateway identifiers in the selected configuration. Store the session key, Google secret and model access token as Worker secrets. The staging-only `TEST_SIGNIN_KEY` must never exist in production. Verify the Google redirect URL against the deployed origin. The setup script also prints the GitHub environment secret names; Worker secrets and GitHub secrets are separate.

When connected apps are enabled, provision the `OAUTH_KV` namespace. Setup prints its identifier; place that identifier in the selected environment's binding. Configure `APP_ORIGIN` as an exact HTTPS origin, `MCP_ENABLED=true`, and the `global_fetch_strictly_public` compatibility flag. Configure `MCP_ALLOWED_ORIGINS` only for browser clients that need cross-origin MCP access; it is a comma-separated list of exact HTTPS origins. Native clients without an Origin header still work. Keep OAuth storage configured during deletion cleanup even if new connections are disabled.

```sh
node scripts/validate-config.mjs --environment staging --purpose deploy --report config-report.json
```

The preflight reports `ready` or `pending`; readiness is configuration evidence only. Gateway payload headers do not control every logging destination. Inspect gateway logs, Worker logs and any Logpush configuration using synthetic data before allowing real career uploads. Leave body collection and caching disabled. Model recordings must also contain synthetic data only.

For a staging-only deployment using the secret-protected test sign-in before Google is configured, add `--test-signin-only` to the deploy preflight. This requires `ALLOW_TEST_SIGNIN=true`; it does not waive Cloudflare Access or spend checks and is rejected for production. Without Google configuration, Google sign-in remains unavailable and must still be verified before release. The flag only changes preflight; it does not disable a Google client that is already configured.

For an isolated, non-model staging smoke deployment, `--smoke-only` is a separate deploy-preflight mode. It requires test sign-in, the pilot budget binding and `PILOT_SHARED_BUDGET=true`, a zero daily spend cap, invite-only mode, billing and MCP disabled, and empty Google configuration by default. To test Google sign-in explicitly, add `--smoke-google` alongside `--smoke-only` and configure a nonempty Google client ID and the Worker secret; this flag is rejected outside staging smoke deployment. Cloudflare Access may be omitted entirely, leaving admin routes unavailable, or configured with both a valid HTTPS team origin and a nonempty audience; a partial pair fails preflight. Without that opt-in, Google sign-in remains unavailable; model requests and Browser Run fail closed in either smoke mode. It is not a live-model evaluation or a release gate. Before deploying, list the staging Worker's secret names and verify none shadow these variables; the evaluation-secret check alone does not check all of them. Verify the deployed bindings, settings, and denial paths before use, and use synthetic data only. The mode is rejected for production and does not establish that older deployed code or Workflows have drained.

Normal deployment and staging lifecycle preflight require a finite positive `DAILY_SPEND_CAP_USD` in the selected Worker configuration. The committed value is zero, so paid work remains disabled until the operator sets a cap. Bind all four per-Vault Workflows (`DISTILL`, `TAILOR`, `DOCUMENTS`, `REEMBED`). The public production workflow also refuses configured restore fences; maintenance deploys follow the fenced replacement procedure below.

### Reading a posting from a link

`POSTING_READER_ENABLED=true` lets a signed-in person have the Worker fetch a job posting's page and read the schema.org JobPosting on it. It is absent from every environment, so the feature is off and the app doesn't offer it. `scripts/validate-config.mjs` refuses it in production configuration (`POSTING_READER_ROLLOUT_UNVERIFIED`).

Enable it in staging first by adding the variable to `env.staging.vars`. Before lifting the production guard, confirm against the deployed staging Worker that each of these gives "couldn't be reached" and that nothing inward is contacted: a public name that resolves to a private address, one that resolves to a cloud metadata address, a redirect to each, and an address on this app's own zone. The address rules, redirect handling, size and time limits are covered by unit tests; what the platform's outbound requests can reach is not something a local test can show. The reader identifies itself with a `Resumatic/1.0` user agent and sends no cookies.

### Dividing lines in shadow

`SPLIT_SHADOW_ENABLED=true` has the reading of an upload also work out how its lines divide into separate claims, and keep what passes every check in shadow: stored in the person's vault to be measured, shown to nobody and read by nothing ([splitting.md](splitting.md)). It is absent from every environment, and `scripts/validate-config.mjs` refuses it in production configuration (`SPLIT_SHADOW_ROLLOUT_UNVERIFIED`) until it has been measured on lines given with consent and the privacy notice names what is kept. Switched on, every upload makes extra model calls on the extract and judge routes and is marked ready after them. A failure in it never fails an upload.

## Billing configuration

Billing stays disabled unless `BILLING_ENABLED=true` and all required values are valid. Provide `APP_ORIGIN`, `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, an explicit `STRIPE_API_VERSION`, and `BILLING_PLANS_JSON`:

```json
{"free":{"generationLimit":3},"paid":[{"id":"pro","priceId":"price_REPLACE","generationLimit":50}]}
```

The numbers are an example deployment configuration, not a pricing decision. Use allowlisted recurring Stripe prices. `generationLimit` covers all generated outputs. There are no trials. An active subscription alone does not grant paid access: a settled invoice must establish the paid period. A scheduled cancellation preserves access through the paid end date; delinquency does not create a new quota period. Configure the Stripe portal for payment details and cancellation. Enable plan switching only after its proration and entitlement behavior has a separate tested policy.

Webhook verification uses the exact request body, all `v1` signatures and a five-minute timestamp window. Reconciliation uses current Stripe state; delivery timestamps do not order subscription events. Duplicate delivery must preserve the settled invoice and quota bucket. A paid invoice for a future service period is queued by invoice ID without replacing the current paid period; its subscription and invoice are fetched again at the boundary. A Vault also rejects a paid quota bucket whose start is in the future. An older future-period record that lacks its invoice ID cannot automatically restore a paid period already displaced by older code; reconcile the account with Stripe. Validate checkout, cancellation, duplicate and reordered events in Stripe test mode, then attach evidence from one live payment and cancellation to the release gate.

Failed billing events and failed entitlement deliveries are deferred before the next batch, so a persistent failure does not permanently occupy all 20 batch slots. Delivery backoff is bound to its revision: a later cancellation is eligible without waiting for an earlier revision's retry. These are local scheduling safeguards, not a delivery-time guarantee under sustained load or a substitute for alerting and Stripe reconciliation.

Checkout keeps a durable server-generated intent and recovers a lost response by its Stripe metadata. Cancel a pending checkout before changing its plan. A confirmed expired session receives a fresh key; a creation with an unknown outcome older than 23 hours requires operator reconciliation and cannot start another payment. Resolve the original Stripe session and customer before clearing any intent. Account deletion expires open checkout sessions, cancels subscriptions and verifies their current state during both deletion sweeps; missing billing credentials or a remote failure keeps deletion pending.

Each Checkout creation also installs a durable Vault dispatch fence before contacting Stripe. A successful response records its exact session ID in the same transaction that settles the fence. Both deletion sweeps check those IDs directly, expire open sessions, and check and cancel any resulting subscriptions; they do not depend solely on list visibility. Account destruction and maintenance wait while creation is in flight; an error or interrupted response leaves a fence because the creation may still arrive later. Retrying does not clear an older uncertain attempt. Operator reconciliation must establish that all old requests can no longer create sessions and resolve any resulting payments before any fence is removed; there is currently no automated procedure that establishes this. This protection requires every deployed writer to use the fence, so mixed-version rollout, older checkout history and real Stripe behavior remain release gates.

Customer creation, including deletion's idempotent recovery request, uses the same kind of durable fence. The returned customer ID is persisted atomically when its own fence is settled, even if access was closed while Stripe was responding. Failed or interrupted creates remain fenced, including after a later successful retry. Existing or mixed-version customer creates did not install this fence; provider reconciliation and rollout verification remain necessary before relying on deletion evidence.

An unknown customer creation older than 23 hours also blocks automatic deletion recovery, because Stripe may have pruned its idempotency key. Locate the original customer in Stripe using `metadata.account_uid`, inspect all matches and resolve any duplicate customers or subscriptions. The Access-protected `POST /admin/vaults/:id/billing/customer` accepts `{ "customerId": "cus_..." }`; the server verifies the customer metadata against the Vault owner before recording it. This repair records one verified association, not proof that other matching Stripe customers were cleaned up. The operator must resolve all duplicates before accepting deletion evidence.

Stripe cleanup checks session and subscription ownership before expiring a Checkout Session or canceling a subscription. If a session completes while expiry is in flight, cleanup checks its linked subscription directly instead of relying only on the customer subscription list. A completed payment or subscription session with unpaid or unknown payment status remains pending, while other known subscriptions are still canceled; [Stripe documents separate events for delayed payment success and failure](https://docs.stripe.com/payments/existing-customers?platform=web&ui=stripe-hosted). These checks do not establish a complete provider inventory or settlement of every invoice. Cleanup does not erase Stripe customer, invoice or payment records. Retention of those external records, Workflow history, gateway metadata and storage recovery history remains a separate review even after application-store counters reach zero. Keep the deletion acceptance check pending until that review states the applicable retained stores and windows.

## Live model and staging checks

Cloudflare catalog IDs are exact: the defaults use `anthropic/claude-haiku-5.5` and `anthropic/claude-sonnet-5.5`, not the hyphenated provider-native names. See Cloudflare's [Haiku](https://developers.cloudflare.com/ai/models/anthropic/claude-haiku-5.5/), [Sonnet](https://developers.cloudflare.com/ai/models/anthropic/claude-sonnet-5.5/) and [catalog lookup](https://developers.cloudflare.com/agents/models/ai-sdk/) documentation. The unified [chat completions endpoint](https://developers.cloudflare.com/ai-gateway/usage/rest-api/) accepts third-party models, but the Claude model pages show the native Messages request format; validate the actual gateway translation and JSON responses in the budgeted staging run. Local tests do not establish interoperability or schema compliance.

The default judge `openai/gpt-5` is scheduled for removal on December 11, 2026, according to [OpenAI's deprecation notice](https://developers.openai.com/api/docs/deprecations/). Choose and evaluate a replacement before that date. OpenAI recommends GPT-5.6 Sol, which [Cloudflare lists as Responses-only](https://developers.cloudflare.com/ai/models/openai/gpt-5.6-sol/), so it needs a Responses-format request rather than the existing Chat Completions format.

The shared model adapter has an **opt-in**, locally tested Responses path for `openai/gpt-5.6-sol`. It sends `store: false` and retains the gateway's payload-log and cache controls. It also requests OpenAI's `prompt_cache_options: { mode: "explicit" }` with no breakpoints to disable the provider's separate implicit prompt cache; [OpenAI documents this opt-out](https://developers.openai.com/api/docs/guides/prompt-caching/). Cloudflare's pass-through of this option has not been verified: confirm it and provider retention before processing career text. It is not the default judge: evaluate its output, failure handling, retention and latency through the configured gateway before selecting it. This model is intentionally absent from the built-in price table: its [Cloudflare pricing](https://developers.cloudflare.com/ai/models/openai/gpt-5.6-sol/) varies by input length and includes a separate cache-write rate, which the two-number table cannot represent exactly. Supply a current, conservative upper-bound override through `MODEL_PRICES_JSON` for the Worker and `EVAL_MODEL_PRICES` for evals, with the existing provider billing controls and daily price review. Local tests do not verify gateway compatibility, provider retention or final invoicing.

Model calls require explicit positive `EVAL_BUDGET_USD` and integer `EVAL_MAX_CALLS`. The Node model adapter reserves a conservative known-price bound before each HTTP attempt, including schema retries. Unknown prices require `EVAL_MODEL_PRICES` with input/output USD per million tokens. `CF_ACCOUNT_ID`, `CF_AI_TOKEN` and `AI_GATEWAY_ID` are also required. Missing configuration produces `pending` and no live calls.

Worker model accounting uses the configured price table for settlement. If the token counts needed by that table are missing, the attempt remains unknown with its reservation retained; it is not priced using a different built-in rate. A call with no output-token bound is refused before dispatch if its configured output price is positive. These safeguards do not establish provider billing bounds or make a per-vault reservation a provider-side hard cap.

The live CI evaluation and staging E2E jobs are deliberately blocked before their model calls: their budgets do not yet enforce one combined authorization. A deployed staging Worker therefore does not imply a passing E2E. The first-pilot runner keeps a persistent local ledger across extraction and tailoring, but its real shared-coordinator adapter is also blocked until the staging URL is proven to reach the Worker's account and ledger namespace and provider bounds are established. Its local ledger does not cover staging E2E or other hosts. Do not run the direct commands below, the E2E, or another host against the same authorization without accounting for all prior reservations and provider-side budget.

Before creating its one-shot local campaign marker, the first-pilot preflight checks that the shared ledger has enough remaining weighted calls for the minimum extraction and tailoring runs. The Node adapter now sends Workers AI requests to the named gateway with cache and payload-log suppression headers, and reserves six attempts for each request, multiplied by Clairic field count. This intended routing and header behavior have not been verified against the deployed service. The exploratory pilot evaluates extraction and its judge separately, then exercises the production analyze, select, rerank, write and verify functions using a manually specified synthetic confirmed fact. It does not test conversion, Workflows, real uploads or the extraction-to-tailoring handoff. The shortest successful LLM extraction and confirmed-fact tailoring path consumes 48 of the authorized 50 weighted attempts; a second matched requirement, schema retry or repair can exhaust the remaining capacity. Clairic and judge add-on strategies cannot meet this conservative minimum within 50, so preflight rejects them. The local stand-in shows one possible path, not that real models will take it. The capacity check is not a reservation: concurrent consumers or actual model costs can still prevent completion.

The first-pilot runner also requires `CF_GATEWAY_READ_TOKEN`, an account-scoped token with permission to read the named AI Gateway configuration. It reads that gateway by the configured staging account and gateway IDs, and requires an explicit `logpush: false` and an explicitly empty or null `otel` configuration before creating the campaign marker. The management token is not passed to evaluator subprocesses. [Cloudflare documents that Logpush exports are unaffected by the per-request logging headers](https://developers.cloudflare.com/ai-gateway/observability/logging/logpush/), and [OTEL spans can include prompts and completions](https://developers.cloudflare.com/ai-gateway/observability/otel-integration/). Missing fields, permissions, malformed replies or enabled exporters leave the pilot pending. The read is only a point-in-time prerequisite: gateway settings can change immediately afterward, and the response does not establish a complete account-wide log inventory, provider retention, or the absence of older exports. Disable and audit all relevant destinations, including account-level jobs, before processing career text. This check does not protect ordinary production traffic or replace the synthetic end-to-end privacy audit.

A staging-only `PilotBudget` Durable Object and separately authenticated `/auth/test/pilot-budget/*` endpoints provide a shared, fixed-name ledger. Its secret, `PILOT_BUDGET_KEY`, must be at least 32 bytes and can be set interactively with `npx wrangler secret put PILOT_BUDGET_KEY --env staging`; never set it in production. Initialization fixes a maximum of $10 and 50 attempts (or smaller limits) and cannot reset usage. Reservations are nonrefundable, duplicate attempt IDs are refused, and reported unknown or excessive usage freezes the ledger. A crash can leave a charged reservation pending without automatically freezing it. The API accepts accounting metadata only, never prompts or responses.

After configuring staging access, `node scripts/inspect-pilot-attempts.mjs` reads at most 50 reservation records through that authenticated coordinator. It checks the staging origin and active deployment bindings first and prints only reserved amounts, states and keyed attempt fingerprints, not raw attempt IDs or provider inputs. The fingerprint is HMAC-SHA256 with `PILOT_BUDGET_KEY` over the UTF-8 string `resumatic-pilot-attempt-v1:` followed by the attempt ID; compare it privately with the local Node ledger or Vault attempt ID. The secret must remain private and may rotate, changing fingerprints. The records form one point-in-time coordinator snapshot, which can change immediately afterward. The report always remains pending: it cannot prove that the HTTPS endpoint reaches the intended namespace, settle an unknown charge, identify provider-side retries, or authorize another request. Never settle a pending attempt merely from an absent log or a timeout.

To compare with this host's one-shot Node campaign ledger, set `PILOT_LOCAL_LEDGER` to its absolute `first-staging-evals-budget.sqlite` path before running the same diagnostic. The owner-only ledger is opened read-only and compared by keyed fingerprint, reserved amount and state; the report never includes raw attempt IDs or the path. New local ledgers also store each attempt's retry-weighted call reservation, which must agree with the coordinator before the row is reported as matching. Older version 2 ledgers never recorded individual weights; those rows are explicitly marked as having unknown calls. They reject new reservations but still allow settlement and freezing of existing attempts; their existing campaign marker is not replaced or reset. The local audit accepts the expected SQLite DELETE journal mode and at most 8 MiB across the ledger and its sidecars; malformed, oversized, non-private or inaccessible files are reported as unavailable. These checks do not protect against a compromised process running as the same user. Other hosts and Worker attempts may appear only in the coordinator. The two snapshots are taken at different times, so a mismatch can be a concurrent change; a match does not establish complete coverage, settle an attempt or authorize spending.

Gateway request usage is still required to settle a reservation. Missing or invalid usage freezes the campaign; it is never treated as a free or successful call. In particular, current Workers AI output documentation does not establish that synchronous embedding and reranker responses always contain usage. [Cloudflare describes gateway spend limits as eventually consistent and estimates as best effort](https://developers.cloudflare.com/ai-gateway/features/spend-limits/) and says [prepaid balances can become negative](https://developers.cloudflare.com/ai-gateway/features/unified-billing/). Neither a gateway rule nor prepaid credits alone prove the user-authorized $10 ceiling. Establish complete provider-side bounds independently before dispatch.

Node evaluators and opt-in Worker pilot mode have reservation adapters, but **real pilot dispatch remains blocked in code** pending verified same-ledger identity and provider-side bounds. The Worker mode rejects conversion and Workers AI models, including `@cf/` IDs on chat routes, because their costs or hidden attempts are not bounded; ordinary non-pilot staging traffic bypasses this ledger. Browser Run Quick Actions are billed separately in [browser hours](https://developers.cloudflare.com/browser-run/pricing/) with billing-period rounding, and their cost is outside the model ledger. While `PILOT_SHARED_BUDGET=true`, an uncached PDF request fails before Browser Run; a PDF already stored under the current snapshot-bound cache key remains downloadable, and the preview and Word export do not invoke Browser Run. Older unbound PDF caches need regeneration outside pilot mode. A privileged operator can also bypass the ledger through direct provider requests, storage deletion, or a different account or Durable Object namespace. A provider-side billing limit, verified cost and retry bounds, complete call coverage, and end-to-end staging validation remain required; keep the paid CI guard in place.

Set `CLOUDFLARE_ACCOUNT_ID`, a read-only `CLOUDFLARE_API_TOKEN` with Worker deployment, version and routing metadata access, `STAGING_URL`, and `PILOT_BUDGET_KEY` privately in the environment. Per-format extraction routing is opt-in. `EXTRACTOR_BY_FORMAT` is a JSON object whose optional keys are `pdf`, `docx`, `linkedin`, and `ocr`, and whose values are valid extractor IDs, for example `{"pdf":"clairic","docx":"llm:default"}`. This example is configuration syntax, not a recommendation. An unmapped format uses `EXTRACTOR`; the configured vault-hash experiment still overrides the format default for its challenger cohort. All routes are validated, and a source's chosen strategy is pinned when its upload is committed, including across Workflow retries and later deployment changes. Do not set format routes until the corresponding real-format evaluation has met its promotion gates.

Conversion-quality warnings are heuristics, not a determination that a file was read correctly. Cloudflare's documented Markdown conversion response does not provide a PDF page count, so ordinary PDF page counts remain unknown. OCR sources record the number of page images actually submitted, not a claim about the original PDF's total pages; sparse-text checks can use that known image count. Calibrate the thresholds with the real dataset before relying on them for format-specific decisions.

Use the extraction CLI's offline mode for harness development; it is not a model-quality result. Keep real consenting-user fixtures outside Git. Promotion reports must name model IDs, prompt hashes, split and repetition count. Held-out promotion results cannot be replaced by development results or hand-picked examples.

The extraction CLI requires an explicit `--live` argument and, for live runs, the staging environment; inherited extraction or recording flags alone do not enable model calls. Its environment name does not prove that shell-provided account and gateway IDs belong to staging. Direct live calls remain blocked by the shared-identity guard; verify those IDs and privacy settings before changing that guard. It serializes CLI runs in the working directory and replaces its fixed JSON and Markdown reports with pending markers before starting a run or promotion assessment. Each CLI evaluation writes into a private per-run directory before the parent publishes its reports. A failed child restores the pending markers and leaves the lock in place. Treat reports as unfinished while `.extract-report.lock` exists; after an interruption or failed run, confirm that the CLI, Vitest child and any worker descendants have stopped before removing the stale lock and rerunning. The JSON marker is authoritative if report replacement is interrupted. Direct Vitest invocations, including the pilot runner, do not take this lock and must not run concurrently in the same directory; the pilot also remains subject to its separate paid-call guards.

Extraction retains the full source line for non-skill facts and merges proposals on the same line and role. Skills require a complete item under a same-line or immediately preceding `Skills` or `Technical skills` heading and no detected qualifier on the relevant nearby lines. LinkedIn skills use parser-identified CSV cells. These conservative rules can miss skills in other layouts and merge distinct facts; their English qualifier checks do not prove meaning or cover all languages or multiline context. Measure their effect and audit unsupported claims on the held-out dataset before promotion.

`MODEL_TRANSCRIBE` is optional. Configuring a model does not accept its license. For example, the Workers AI Llama vision model requires an operator to accept its terms before its first image request. Keep OCR unavailable until that step and a budgeted image check are complete. Image-derived proposals have weaker evidence and must retain that label.

Configure the selected environment's `APP_ORIGIN` and `CF_ACCOUNT_ID`, the matching origin (`STAGING_URL` for staging), `CLOUDFLARE_ACCOUNT_ID`, and Access service-token credentials privately. Local configuration matching does not verify DNS, TLS routing or WAF body logging; use a trusted host and network and verify logging first. An inventory does not fence writes or authorize deletion.

For legacy sharded accounts without a V3 creation binding, final deletion can remain pending when the captured invitation generation still exists: the system cannot tell whether it predates deletion. Earlier cleanup may have completed, but do not report erasure as complete. An administrator must verify whether that invitation is still wanted, then explicitly revoke it or reissue it; the latter rotates its generation and preserves the new grant. The alarm retries finalization. This is an interim reconciliation step, and older deployed finalizers must be drained before relying on the migration guard. Global-home cleanup now has a fenced cross-shard inventory, but it remains disabled until a verified runtime drain and the explicit rollout assertion described below. Do not treat local diagnostics or a read-only inventory as proof of a deployed drain.

The deletion audit acquires a per-report lock and publishes a pending report before probing. Treat any report with a corresponding `<report>.lock` directory as unfinished, even if the report itself says it passed: a crash can occur before the pending marker is published. If a lock remains after an interruption, verify that the old process has stopped, remove the stale lock, and rerun the audit. Release evidence is operator-attested; the release check does not read this local lock automatically.

The staging E2E is currently blocked in code before sign-in or network requests, including when invoked manually with credentials. The per-Vault lifetime limits and daily cap alone do not prove that Worker calls and Node evaluations share one ledger, bound all provider attempts or cover separately billed Browser Run. Before replacing this guard, verify the staging account and shared-ledger binding for every model path and deployed version, establish provider-side limits and retry/usage bounds, and verify a Browser Run billing bound consistent with the existing authorization. An environment flag or a per-Vault budget is not that evidence. The future run requires `STAGING_URL`, `TEST_SIGNIN_KEY`, and explicit positive `EVAL_BUDGET_USD` and `EVAL_MAX_CALLS`; it also fails closed if the test-only budget endpoint is unavailable. The E2E records the Vault run ledger before deletion and distinguishes account access revocation from storage erasure. An upload whose acknowledged R2 put finishes after Vault closure is deleted when the Vault authoritatively rejects completion as gone; ambiguous RPC failures retain the key to protect already-committed sources. This cleanup is best effort: a Worker crash or unknown R2 outcome can leave a late write, so it does not prove quiescence. The audit additionally needs Access service-token credentials. Its Workflow probe checks every supplied ledger ID, including superseded attempts, but cannot independently prove that the captured inventory is complete. Therefore, even all-zero counters remain pending until an independent complete-inventory attestation exists; missing counters, an unavailable endpoint, or an incomplete retention review also remain pending.

The Vault authenticates the session and atomically records a deletion intent, closes normal access, and schedules a recovery alarm before the Worker calls the Directory. This orders deletion against sign-out everywhere. If the Worker stops before that call, the Vault alarm schedules another retry before contacting the Directory, then uses its persisted owner and Vault ID; the Directory verifies that ID against its current account record. The Vault removes its retry after Directory acknowledges a durable cleanup alarm. A scheduling failure rolls back the intent. After an intent is committed, the same session can retry deletion even if a control-plane failure returns an error, while ordinary API access remains closed. The Directory commits its deleting state and an alarm in one SQLite-backed storage transaction, quiesces the Vault, and the Worker confirms quiescence before returning HTTP 202. Directory alarm handlers also arm a retry before external calls; an extra idle alarm may run after cleanup. When no earlier alarm exists, retries and cleanup are scheduled for 60 seconds later; platform delays can make them later. Only one alarm handler runs per object at a time: a pre-armed retry does not by itself resolve a permanently stalled call, and in-flight timeout and termination behavior still needs staging verification. An acknowledgement lost after the Vault closed can make the old session unusable for ordinary access even though deletion returned an error. Alarm retries also quiesce before checking an unresolved initialization marker. Those markers and the Workflow dispatch fences still prevent destruction; access revocation does not certify erasure. Verify the storage transaction, retry, rollout and mixed-version assumptions on staging before relying on them in production; older Worker and Vault versions do not enforce the intent protocol.

Configure `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_API_TOKEN`, and `STAGING_URL`; the configured account and manifest origin must match. Use a narrowly scoped read-only token and do not put credentials in the manifest or command line. This read-only diagnostic lists all visible instances of the four per-vault Workflows and fetches each instance's simple metadata, including its parameters, to attribute instances to the vault. It makes up to one detail request per visible instance and stops at the explicit bound. Provider responses may transiently include other users' data in memory; the report contains only IDs, counts and fixed codes, with no payloads. An unattributed instance, missing ledger ID, unexpected instance or parameter mismatch needs review. The per-vault comparison retains visible findings when pagination metadata is absent or a full page has no cursor; `paginationUncertain` identifies those bindings, and `scanLimited` identifies a scan stopped at its bound. For positive evidence in fleet Workflow state, run `node scripts/inspect-fleet-workflows.mjs --environment staging --manifest deletion-manifest.json --max-instances 50 --report fleet-inventory.json` with the same account, origin and read-only credentials. Instance details may contain truncated step previews. An optional `--max-full-steps` from 1 to 100 fetches full output for recognized fleet step names; the default is zero. Every result remains pending: provider output, pagination and in-flight execution do not establish complete inventory, retention expiry or erasure. Confirm the API response shape and access permissions in staging before relying on positive findings.

Workflow dispatch is fenced before external creation so closing or moving a vault waits for acknowledged in-flight creates. A rejected or interrupted create has an unknown outcome; a missing or terminal instance observed once does not establish that a delayed create cannot still arrive. Cloudflare documents duplicate-ID rejection only while an existing instance has not passed its [retention period](https://developers.cloudflare.com/workflows/build/workers-api/); observing one instance is not a permanent ID fence. For an open vault with a starting run, the alarm can retry creation with the same instance ID at most three times with persisted backoff. Before the first retry it installs a separate permanent uncertainty fence. Neither a successful retry, a duplicate response, nor an acknowledgement from the original call clears that fence. A SQLite trigger also prevents older unconditional cleanup from deleting the original marker while the retry fence exists. These protections require deployed validation; older code may bypass them, so do not rely on mixed-version recovery without proving old instances have drained.

The retry can restore work but does not resolve erasure, move or cancellation. Deletion and maintenance remain pending while any marker exists, and cancellation remains pending even if one lookup reports the instance absent or terminal. The migration conservatively marks every historical Workflow run and legacy source/resume run ID, including terminal runs; affected accounts require a future provider-verified reconciliation procedure before deletion or transfer can finish. No operator override exists today. The application reports an unconfirmed start after 30 seconds while a starting run retains a marker. Initial dispatch schedules an alarm before creation, but an interruption during alarm scheduling can still leave a marker requiring operator attention. Retrying may lead to additional provider processing or model attempts; local attempt reservations enforce configured application spend limits but do not guarantee a provider invoice ceiling or that a model is called only once. Confirm same-ID uniqueness, post-create visibility, billing controls and mixed-version behavior against the live provider before rollout, and keep Workflow inventory and erasure audits pending.

Directory initialization attempts are also fenced before cross-object calls, and account state is rechecked after acknowledgement. A sign-in or replacement preparation can retry initialization for the same persisted vault and owner after an unknown outcome; concurrent attempts share one call. The earlier attempt's marker becomes permanently sticky before a retry, and an acknowledgement from this code does not clear it. A SQLite trigger also prevents an older unconditional delete from removing a sticky marker; it is verified locally and must be tested on the deployed platform. Older code may bypass the fence altogether, so do not rely on recovery across a mixed-version deployment without first proving older instances have drained. This may restore access but deletion or transfer remains blocked until a provider-verified reconciliation procedure exists. The migration conservatively fences **all** existing vaults, replacement targets and retired vaults. Historical orphaned attempts whose Directory rows have already been removed cannot be inventoried by this migration. Any future partial-erasure path also needs a durable checkpoint for a crash between `destroy()` and the Directory's state update; treating an empty vault as closed without that evidence can hide a late initialization. These limits remain release blockers.

Workflow calls must identify an existing run with the correct kind and target. Calls from older in-flight Workflow code that lack this identity, or refer to legacy rows without a run ledger, fail closed even when a previously completed step is replayed. Such interrupted work needs a fresh run after reconciliation; upgrading the Worker alone does not migrate an in-flight execution or resolve its dispatch fence. Preserve old deployments until a staged upgrade and recovery plan has been verified.

## Metrics, alerts and abuse limits

Bind `METRICS` to the selected Analytics Engine dataset and use `METRICS_DATASET` for alert queries. Workflow metrics use `blob1..5` for run ID, step, route, model and outcome; `double1..4` for milliseconds, input tokens, output tokens and integer micro-USD. HTTP metrics use step `http` and a bounded route category. Neither shape contains career text, filenames, IP addresses, raw URLs or credentials.

Completed-run latency uses a separate `run_total` event. The dashboard aggregates end-to-end p50/p95 by run kind and model-attempt p50/p95 by route and model. Alert and cost queries exclude `run_total` so totals do not count model work twice. Unknown cost remains visible instead of being reported as zero. Verify these query shapes against the deployed dataset before accepting latency or spend evidence.

To enable the fifteen-minute alert job, set `ALERTS_ENABLED=true`, `CF_ANALYTICS_TOKEN` with Account Analytics Read, `ALERT_WEBHOOK_URL`, and `ALERT_SPEND_USD_PER_15M`. Optional thresholds are `ALERT_FAILURE_RATE` and `ALERT_HTTP_5XX_RATE` (defaults 0.05), and `ALERT_MIN_ATTEMPTS` (default 20). Unknown model cost raises a separate alert. The webhook receives only window totals and error-category codes. Disabled alerts make no network request. Alerts can repeat while a threshold remains breached; operational acknowledgement belongs in the configured receiver.

Queries weight rows by `_sample_interval`; these are sampled operational measurements, not a billing ledger. Quota and spend reservations in the Vault remain authoritative. The profile, role, and fact reads retry at most twice on transient retryable Durable Object errors, recreating the stub each time; overloaded errors are never retried. The `AUTH_LIMIT` and `WRITE_LIMIT` bindings limit bursts per Cloudflare location. Authenticated writes use the user ID; guest authentication/OAuth requests use an HMAC of the IP address. Shared networks can still hit a guest limit. Missing optional bindings skip burst protection, so configure them before public launch.

## Interview answer provenance

Answers to generated experience questions are saved as confirmed user-authored facts, without consuming an output credit. The vault also retains the originating question and the exact original answer as history. Editing the fact changes the claim used for generation; the original answer remains visible as history and is never used to override the correction. Interview provenance is included in the owner's data export and fenced replacement transfer, excluded from coach shares and MCP tools, and removed with the vault.

`GET /api/export/archive` streams a ZIP containing `vault.json` and the source objects referenced by that snapshot. It accepts at most 128 source records and 100 MiB of member data, plus ZIP overhead. The JSON snapshot is assembled before streaming, so a large vault may reach Worker memory or RPC limits before the archive limit is checked. Source objects are checked by ETag; a missing or changed object, interrupted connection, or failed session check during streaming errors the download rather than completing a partial ZIP. Session checks cannot recall bytes already delivered. Verify streaming and deletion races against deployed R2 before relying on those checks. The existing JSON export and individual source downloads remain available for vaults over the archive limits.

Resume exports, previews and coach shares require immutable evidence for every printed role heading, including empty education sections. Versions created before role evidence was recorded remain visible to the owner and in the owner's data export, but must enter grounding review before they can be exported or shared; existing links containing such a version become unavailable. Review requires matching current confirmed roles and rechecked lines. The owner can remove a section (including an empty one) from a new review version when its heading no longer matches; its lines are removed too. A heading cannot be rewritten in place, so generating a new resume is another option. Historical versions and share snapshots are not silently rewritten.

## Uploads and embedding rebuilds

Upload reservations persist the metadata/body digest and a unique R2 key before writing bytes. Retries recover the same source; conflicting metadata fails before replacing an object. Current source and OCR uploads send the bounded body to the Vault, which verifies the original filename and body digest, canonical key and ownership before recording a distinct durable dispatch marker and reservation link for each R2 put. The Vault clears only the acknowledged attempt's marker, without a separate Worker settlement RPC. It registers the bounded put-and-settle promise with `waitUntil`; Cloudflare documents that [pending I/O can keep an object active after a disconnect](https://developers.cloudflare.com/changelog/post/2026-10-01-pending-io-keep-alive/), but this is not proof that the put will settle or survive failure. An unknown put outcome keeps its marker and blocks vault destruction. Expired-upload cleanup can proceed for other linked reservations, but an older or unlinked source marker blocks it globally. Replacement-copy puts use the same fence and an import waits for all content pages before enumerating its sources. A crash before dispatch can also leave a marker, and there is no automated way to prove that such an attempt is safe to clear. A new Worker cannot fall back to an older Vault without the write RPC. The up-to-10 MiB upload or approximately-12 MiB OCR body crosses RPC and can be buffered in both isolates; verify concurrency, memory, latency and Durable Object duration charges on staging. Validate interrupted upload, replacement and deletion races against staging R2 before accepting these safeguards as live evidence.

Replacement copies also keep the put-and-settle promise alive with `waitUntil` where the runtime permits. A null response or an acknowledgement with the wrong key, size or SHA-256 leaves that attempt fenced; a subsequent successful copy or visible object does not settle it. Source reads, copy puts and verification-head provider errors are reduced to fixed codes and messages. This improves the chance of recording a real acknowledgement after a caller disconnects but cannot recover a crashed object or an ambiguous provider result.

Each paginated deletion sweep makes a fresh first-page listing and remains pending if that listing is nonempty or incomplete. This catches objects already visible after the sweep; it cannot prove that an unresolved write will not commit later.

After a deleting Vault is quiesced, the Directory makes a preliminary R2 sweep and attempts to cancel already-recorded billing and delete known Workflow instances while it separately attempts close. The preliminary billing read does not create a Stripe customer. These operations can reduce outstanding data and future billing while a fence remains unresolved, but they do not mark the Vault swept or replace the post-close billing check, Workflow termination or final R2 sweep. Deletion, retirement and finalization use separate lanes with up to four concurrent operations each. Each free slot starts another item, even if a different operation remains unresolved. Four stalled operations in a lane can still hold its remaining items, and the alarm awaits every lane. The second finalization pass waits for the entire retirement lane, so an account whose own retirement has finished can still be delayed by an unrelated stalled retirement. A retry alarm is scheduled before external calls; progress also depends on the runtime delivering it or resetting an unresolved invocation. A swept account waits while any retired row names its owner or its Vault ID, and finalization rechecks that condition after external calls. If a retired row names a current Vault, retirement is held for operator review rather than closing it. A timeout cannot establish that an already-issued provider operation has settled, and must not authorize destruction.

A due final sweep that remains blocked or fails is rescheduled at the retry interval, rather than repeatedly scheduling an alarm in the past. This bounds retry frequency; it does not settle any pending provider operation.

Current account deletion also retains the closed Vault through the delayed final sweep, checks its owner before that sweep, then destroys it. A durable per-vault phase records an acknowledged destroy before later billing and identity cleanup, which may then retry. A SQLite trigger also blocks deletion of a swept Directory row until that row has a matching acknowledged-destruction marker; older code may have already issued external operations before it reaches that trigger. A lost destroy acknowledgement remains pending because an empty Vault cannot prove ownership. Preexisting `swept` account rows lack this proof and remain pending for reconciliation; do not invent a marker or sweep them automatically. These local checks do not settle older in-flight writers, cross-shard publication or provider retention.

Current retirement keeps a Vault closed and owner-bound through its first sweep and the configured delay. The second sweep rechecks the recorded owner and outstanding fences before destruction, so its SQLite data remains until that delayed sweep completes. A retired row receives an incarnation ID, and changes to its owner, phase or sweep time during an awaited call hold cleanup pending. Replacement deletion cancels preparing targets before quiescing them, and current cutover checks that the target is still preparing and not retired before publication. Legacy `swept` retired rows do not prove ownership and remain pending for operator review. If the destroy acknowledgement is lost, the owner may no longer be available on retry; that row also remains pending. A newly discovered retired row stops later identity release and the final Directory transaction, but cannot reverse an identity release or other cross-object operation already in flight. Same-owner claims from another Directory, delayed initialization, older code and deployment drain are not proven fenced; validate the full rollout and provider retention before accepting erasure.

Vault alarms pre-schedule a retry before processing pending upload cleanup or Workflow status calls. A failed upload delete remains pending while other candidates continue. Authenticated source, resume, application, document and run status reads, as well as the admin run view, can rearm a missing alarm for an active run; they recheck access after scheduling. This depends on a later poll and does not settle an uncertain Workflow create, prove a complete provider inventory or establish that R2 writes have drained.

New PDF and DOCX exports cache inside the owner's Vault, in 512 KiB SQLite chunks with a 4 MiB item limit and a 16 MiB per-vault limit. Entries are checksum-checked and evicted by last access; oversized exports are served without caching. Each key includes a hash of the checked render snapshot and a renderer version. Unbound legacy Vault and R2 entries are ignored, not deleted; the first request regenerates the output from the checked snapshot, and a PDF regeneration requires Browser Run. Cache RPC failures fall back to rendering only after a session check, and the session is checked again before returning bytes. Replacement does not transfer these regenerable caches. Verify memory, latency, retention and failure behavior on staging.

Earlier deployments could use the experimental `R2_CACHE_FENCE_ENABLED=true` setting to record a marker before a PDF or DOCX R2 cache put. The current export routes no longer invoke that writer, but unresolved markers continue to block destruction and replacement. Current source and replacement-copy puts use the same marker table; older deployed writers do not. `GET /admin/vaults/:id/cache-write-fences` reports marker metadata. Current markers contain a SHA-256 digest of the object key, and the corresponding put carries an opaque attempt ID in [R2 custom metadata](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/); older markers may have no digest. These are correlation hints only: a later put can overwrite metadata and an unseen request can still arrive, so a head or list result cannot settle a marker or prove quiescence. There is no automated clearing procedure for an interrupted call. Production preflight continues to reject the experimental cache setting. The shared limit is 64 unresolved markers per vault; reaching it blocks new tracked writes until the uncertain attempts can be safely resolved.

`GET /admin/vaults/:id/cache-write-correlation` is an Access-protected, read-only aid for comparing those digests with current source or export objects. It scans at most two pages of 100 objects and performs at most 16 object heads; a mixed snapshot scans the vault prefix. Its response omits object keys, filenames and arbitrary metadata, and always remains `pending`. A limited or unavailable scan is not an inventory, and even an exhausted scan and matching metadata are only observations taken at different times. Cloudflare says a [negative R2 read does not wait for or cancel an earlier in-flight put](https://developers.cloudflare.com/r2/reference/consistency/). [R2 Data Access Logs](https://developers.cloudflare.com/r2/buckets/data-access-logs/) are asynchronous and best effort, and can omit events, so missing logs cannot establish that a put failed. Do not clear a marker or conclude erasure from this diagnostic, object metadata, logs or a time delay.

For an account already being deleted, `POST /admin/vaults/:id/deletion-fences` with `{ "userId": "<account-id>" }` gives an Access-protected, read-only snapshot of its current initialization, Workflow, R2 and billing fences. It verifies the Directory's deletion-operation or retirement generation and the Vault owner, then rechecks the mapping after reading the Vault. Workflow lists contain at most 64 IDs per kind of marker; R2 counts are capped at 1,000 and report truncation. Use the cache-write diagnostics above for individual R2 attempts. A missing or ambiguous mapping, changed generation, invalid stored ID, or unavailable object fails the diagnostic closed. The report always says `pending` and does not clear a fence. Its Directory and Vault reads are not atomic and exclude provider history, legacy unregistered writes and retention stores, so even zero counts do not establish erasure or authorize recovery.

An R2 sentinel does not recover these existing writes: they are unconditional, so a delayed write can overwrite it. For a future protocol, a unique per-attempt object initialized with an acknowledged random placeholder could require every data put to match that placeholder's ETag. Deleting it would fence a delayed conditional data put only if nothing can recreate the matching placeholder and all earlier data-bearing writers used that exact condition. An uncertain initial placeholder put can itself arrive after the sweep and leave an object under the prefix, however, so this does not meet the current empty-prefix erasure requirement. A create-only data put blocked by a sentinel can also succeed after the sentinel is deleted. Cloudflare documents [atomic evaluation of conditional writes at commit](https://developers.cloudflare.com/r2/reference/consistency/); the local conditional-put diagnostic models these orderings, but does not establish provider quiescence. A safe recovery needs a provider-backed resolution of all in-flight requests or an explicitly revised storage and erasure contract, and must also handle older unconditional writers.

**Multipart candidate for future deletion fencing, not implemented:** use a separate multipart upload for every remaining R2 write attempt, including uploads, OCR inputs and replacement copies. Create the upload without sending user data, then atomically register its returned upload ID and target key in the open Vault before sending any parts or a completion request. Closing the Vault stops new registrations; deletion must retain its ledger while aborting every registered upload, then sweep the prefix only after every abort or completion has a conclusively safe outcome. A create response that arrives after closure cannot authorize parts or completion. Retries need distinct registered upload IDs; neither a missing object nor a lost response settles an attempt.

This could make registered writes revocable without keeping an object sentinel, but it is not an erasure proof. Before implementation, obtain Cloudflare confirmation that abort and complete for the same upload have a definitive ordering: after a successful abort, or a definitive already-completed/aborted result, no previously dispatched completion can publish an object after the following sweep. Establish which provider responses actually prove that result; an ambiguous failure is not enough. Also establish how to remove parts whose uploads were already in flight at abort and prove their removal. The [Workers API](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/) documents successful abort and completion, not these race guarantees. A create whose response is lost can leave an unregistered, empty multipart upload; even if it cannot contain career text under this protocol, its key and metadata can persist, and a late create can appear after an inventory. The same API reference says uncompleted uploads are automatically aborted after seven days; that does not establish part erasure, storage retention or a complete inventory. Confirm cleanup and retention separately. Prove a rollout drains all old unconditional writers and their in-flight writes before relying on the new ledger, and migrate all write paths without an unfenced fallback. Until those guarantees, recovery procedures, mixed-version behavior and staging tests are established, deletion and replacement remain pending.

**Alternative for originals: Vault SQLite blob storage, not implemented.** Store each original and OCR input as an immutable manifest and bounded binary chunks inside the user's Vault. A Vault method would check the session, open state, reservation and aggregate byte quota and commit the chunks, manifest, source and upload receipt together in a synchronous transaction. Workflow creation remains a separate fenced dispatch. Distill, original downloads and archive streaming would read the same immutable object through authorized Vault calls, with version and revocation checks. Replacement needs bounded, checksum-verified blob transfer and staged publication. The current transfer reader stops accumulating rows at its serialized page limit, but adding large blob rows still needs transfer, memory and recovery testing.

This makes new data writes serializable with Vault closure, but needs a durable tombstone that rejects late initialization and writes after eviction. The current `destroy()` calls `deleteAll()`; writing a tombstone afterward would leave a crash gap. A different atomic cleanup and tombstone protocol must account for all application tables, hidden storage and alarms, and the audit must recognize only the approved non-user-data marker. Review whether retaining that marker and the platform's [30-day point-in-time recovery](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/) meet the erasure contract. Row deletion alone does not establish retention expiry.

The [SQLite limits](https://developers.cloudflare.com/durable-objects/platform/limits/) are 2 MB per row and 10 GB per paid-plan object; the [FAQ](https://developers.cloudflare.com/durable-objects/reference/faq/) states a 1 GB per-object free-plan limit. The current maximum of 50 sources, with 10 MiB uploads and OCR inputs around 12 MiB, can approach 600 MiB before other data and storage overhead. Add aggregate limits and headroom, and test `SQLITE_FULL` recovery. [RPC](https://developers.cloudflare.com/workers/runtime-apis/rpc/) has a 32 MiB serialized message limit and [Workers](https://developers.cloudflare.com/workers/platform/limits/) have 128 MB per isolate, shared across requests; profile chunking, streaming, transfers and concurrent load. Paid [SQLite storage](https://developers.cloudflare.com/durable-objects/platform/pricing/) is $0.20 per GB-month beyond included usage versus $0.015 for [R2 Standard](https://developers.cloudflare.com/r2/pricing/), before operation costs and allowances. Validate latency and cost before adopting this alternative.

Migration would require dual reads, all new write paths switched together, checksum-verified copying of old originals, and a demonstrated drain of old Worker and Workflow writers and their provider-side in-flight puts before sweeping legacy R2 objects. Neither a new Vault backend nor an empty R2 listing settles old puts. Test interrupted and duplicate RPCs, closure during upload, rendering and replacement, restart and eviction, corrupt or incomplete chunks, quota failures, and download revocation on staging. This remains an unverified design, not an erasure guarantee.

Embedding rebuilds stage vectors per Vault while serving the previous generation, then activate only a complete generation. Fleet dispatch must use stable run IDs, bounded batches and the same model-budget reservations; failures stay resumable. Run a small staging canary and verify generation activation, cancellation and account deletion before starting a fleet rebuild. Rebuilding embeddings is a paid model operation and needs an explicit configured budget.

## Directory capacity rollout

**Do not roll out shard changes yet.** Local tests now reject two previously reproduced delayed Google creation paths after the new migrations activate, but older versions and unmigrated objects remain a risk and need a verified drain. Existing global user IDs remain global; new shard-prefixed user IDs permanently identify their home. Returning `DIRECTORY_SHARDS` to `1` disables placement of new users into shards; it does not move existing users. Admin listings must still query all seventeen Directory objects after rollback. Do not change the fixed shard count to a different number.

The production deployment workflow rejects sharded placement in the checked-in configuration and rejects a `DIRECTORY_SHARDS` Worker secret, whose value it cannot inspect. Remove any such production secret and use the checked-in configuration before deploying. This guard does not prevent out-of-band deployments or resolve pending requests and existing sharded users.

Invitation inventory is separately gated. With `INVITE_INVENTORY_DRAIN_VERIFIED` absent, cleanup of an exclusive, still-matching global invitation stays pending; do not interpret that as completed erasure. Set it to `verified-v1` only after independently verifying that all older Worker and Directory runtimes and their dispatched requests have drained, confirming there is no account-reactivation path outside the fence, and testing the barrier, cold-shard initialization, timeout recovery and rate impact on staging. The value is an operator assertion, not proof of those checks. An active barrier temporarily blocks account and identity writes; a target shard seal also blocks writes to its finalization, identity and vault-mapping tables, including unrelated accounts on that shard. Failed or unknown shard closure keeps the barrier in place and the alarm retries. Each Directory inventory is limited to 10,000 users and fails closed for malformed records. Do not manually clear a barrier or shard tombstone to restore sign-in: first reconcile every shard and any delayed requests. Legacy invitation bindings and unbound or orphaned claims still require separate operator reconciliation. New V3 Google shard accounts have a creation-time binding and target seal; changed Google email addresses fail closed pending a supported reconciliation path. Provider retention and the rest of the deletion audit remain pending.

The global Directory checks a deletion epoch captured before issuing Google OAuth state. Deletion and Google identity removal advance the epoch; SQLite guards reject legacy global creation, home-claim and binding writes once active. `test/integration/global-auth-fence.test.ts` exercises a global public-registration interleaving with a synthetic identity. It does not test Google, browser cookies, or deployed mixed-version traffic. Requests served by old code before the relevant objects migrate remain unfenced. Establish a provider-verified deployment and in-flight writer drain before relying on the fence.

A migrated sharded Google deletion releases the home through a versioned coordinator RPC that advances and returns the epoch in the release transaction. A shard-local pending/acknowledged outbox persists it; the shard raises a persistent authorization floor in the same transaction that removes the identity. Migrated SQLite guards reject markerless Google inserts and legacy releases, including the reproduced delayed target calls. Conflicting or unbound homes remain pending for review. A lost acknowledgement can cause another conservative epoch advance and invalidate unrelated sign-ins. `test/integration/shard-auth-floor.test.ts` covers local stale calls, retries and legacy rows. Verify rollout, migration and drain before relying on these guards; they do not constrain old code before its object migrates.

The next global migration atomically advances and stores a one-time rollout epoch. On its first activation after upgrade, each shard obtains that server-side epoch and durably raises its floor before accepting requests, covering the local case of a deletion completed before the shard migrated. This first activation fails closed if the global Directory is unavailable, and the epoch bump requires outstanding Google sign-ins to restart. Local tests cover the bootstrap helper, retry and a synthetic cross-object recovery path; they do not establish deployed input-gate behavior, coordinator outage recovery or a mixed-version drain. Plan and test the migration order before enabling sharding.

The epoch is global: any global account deletion or sharded home release can invalidate unrelated pending Google sign-ins, and the user must restart sign-in. New Google shard claims now carry an opaque coordinator token recorded with the target identity at creation. The current Worker uses claim-aware RPCs to match those tokens before binding an unbound home; this allows a fresh sign-in to recover an interrupted initial bind only when the tokens match. SQLite rejects tokenless binding of a tokenized home by older code after migration. A missing or changed token and a legacy unbound claim require reconciliation; existing bound legacy accounts remain reachable. Old coordinator versions lack the new RPC and old targets do not record tokens, so new creation fails closed across those mixed-version paths. The token is not a dispatch-registration or target-seal protocol: older Workers, delayed calls and abandoned orphan claims still require a verified drain and recovery procedure. The deletion probe counts tokens linked to the account and treats unbound or orphan coordinator tokens and unexpected bind markers as incomplete audit evidence. Account deletion and retention acceptance remain pending.

Production deployment preflight requires the reviewed configuration to set `INVITE_ONLY` to the exact string `"true"` and rejects an opaque Worker secret of that name. This reduces exposure to the demonstrated public-registration path, but invitation changes, already-dispatched calls, mixed Worker versions and other deletion races still need resolution. Invite-only mode is not proof of safe deletion, and out-of-band deployments can bypass preflight.

A V3 shard home bind rechecks that the email is still invited, but the target creation RPC can arrive after a revocation and leave an unbound account. A complete fix would register each creation attempt durably before dispatch, fence new attempts during revocation, seal every registered attempt at its target, and reconcile any already-created account before completing revocation. A seal must leave a tombstone against late requests; unknown results and legacy unregistered attempts remain pending. The existing synthetic placement protocol is a starting point, but its automatic settlement cannot be reused for revoked attempts without changing its semantics. This is an unimplemented design, not a recovery guarantee.

For current code, a new invited account's global home claim rechecks the verified email and writes or reads the claim in one Durable Object operation. A prior invite check alone cannot authorize a claim after the invite was revoked. Older Worker versions do not supply the email, so their new invited-account claims fail closed when the new code is active. Older Directory versions do not enforce the recheck and remain a rollout blocker.

The isolated local diagnostic holds an unregistered creation route, deletes that identity, changes the shard setting, creates a replacement, then resumes the old route. Run it explicitly:

```sh
RESUMATIC_PLACEMENT_DIAGNOSTIC=1 npx vitest run --project integration test/diagnostics/placement.diagnostic.ts
```

After the migrations, the delayed Google call is rejected and the diagnostic passes locally. It contacts no model or other external provider. Ordinary CI does not run it, and one passing diagnostic does not establish rollout safety.

An experimental `PLACEMENT_FENCE_ENABLED=true` path is disabled by default, rejected by production preflight and restricted to disposable `test` identities under `@placement.invalid` with staging-style bindings. It reads a coordinator-wide epoch before identity lookups, then registers a generation and attempt only if that epoch is still current; target tombstones reject delayed registered attempts. Releasing a synthetic claim advances the epoch in the same transaction, so a reservation carrying an earlier observed epoch fails closed. This also makes unrelated synthetic sign-ins holding that earlier epoch retry. Deletion closes that generation, seals its registered attempts, removes the target identity, and uses a durable outbox and release receipt to finish the global claim removal after interrupted responses. `POST /admin/placement/reconcile` seals known attempts, and `/admin/placement/inspect` plus `/admin/placement/cleanup-orphan` support generation-qualified cleanup of an unbound synthetic claim. Cleanup closes registration first and retains a claim if sealing reveals an account. These endpoints require Access and accept synthetic subjects in JSON bodies only. Opaque attempt tombstones and generation release receipts persist indefinitely; their retention and provider behavior require review.

This prototype does **not** distinguish a delayed first epoch-read RPC from a new sign-in after deletion: the coordinator has received no earlier authorization or registration for that attempt. Rejecting the former while permitting the latter requires an observable earlier boundary, such as a trusted epoch captured at ingress or a registered attempt. The first diagnostic below intentionally shows that limitation; its current expectation cannot be met while also allowing an otherwise identical new attempt. The second diagnostic exercises a delayed Google shard request after deletion and invite revocation; the new shard floor rejects it after migration:

```sh
RESUMATIC_PLACEMENT_DIAGNOSTIC=1 npx vitest run --project integration test/diagnostics/pre-reservation.diagnostic.ts
```

The first test still fails for the stated reason; the second passes locally. A replacement for the first must define and exercise a trusted pre-deletion authorization boundary as well as legitimate re-registration. Pre-migration and mixed-version requests may not honor these fences at all. Do not enable this for real identities or roll out sharding until a complete protocol, an operable legacy recovery procedure, retention review and staging evidence address those gaps. A passing local test is not sufficient.

### Extraction experiment feedback

`GET /admin/vaults/:id/extraction-feedback` returns one metadata-only record for each source whose observation began after the feedback migration. It reports the extractor and counts of proposed facts, facts ever confirmed, rejected or edited during the seven days after the source was created, and user-added facts in that period. The confirmation, rejection and edit counts can overlap when a user changes a decision. A manually added fact is attributed once to the most recent observed upload within seven days; this association measures timing, not causation. `windowComplete` identifies sources whose seven-day observation has finished. Existing sources are deliberately not backfilled because their original review timestamps are unknown. The feedback ledger is copied with a fenced vault replacement and erased with the vault.

Administrative invitation revocation requires both the inventory drain assertion and a fresh `INVITE_REVOCATION_DRAIN_VERIFIED=verified-v2` assertion after independently verifying the rollout of the current coordinator, shard and Worker code. These values are operator assertions, not proof. Send `DELETE /admin/invites/:email` with a new lowercase UUID v4 in the `Idempotency-Key` header, and reuse that key for retries of the same request. A `204` confirms completion; a `202` means the durable operation is still pending. Poll `GET /admin/invites/revocations/:operation` using that UUID. Do not reuse an operation ID for another email or for a later invitation. Rotating `SESSION_KEY` also changes the fingerprint used to recognize old operation retries; reconcile any outstanding retries before rotation.

The coordinator seals every known unbound shard claim for that email, including claims from earlier invitations, before removing the grant. A shard account that was created before the seal leaves the operation pending for reconciliation; no automatic orphan deletion or adoption has been proved. Legacy claims that cannot be attributed also block the operation. An active revocation holds the affected email and prevents concurrent invitation inventories; unrelated sign-ins may continue. Do not clear its barrier or shard tombstones to force completion. The assertion and local tests do not establish that old deployed requests have drained.

When every target outcome is known but at least one unbound account already exists, revocation moves to a durable quarantine. Its original email, claims and shard tombstones remain fenced and the operation remains pending, while invitation inventories for other emails can proceed. An unknown or unacknowledged target stays in the active barrier. Quarantine does not delete or adopt the account; deletion audits remain conservative while quarantines exist. Do not remove a quarantine by hand to force a result.

After upgrading, inherited active revocations and quarantines require a bounded local identity rescan before they can progress. The rescan requires the new assertion, verifies each stored operation/email fingerprint and preserves existing shard claims. Identity and attribution writes can be held while scans remain; malformed or ambiguous legacy records may also delay unrelated creation or deletion until reviewed. Rotating `SESSION_KEY` before resolving these operations can prevent their fingerprints from validating. Do not clear a pending scan or quarantine to force progress. Local global accounts that were never bound, including some legacy accounts whose history is ambiguous, remain quarantined; neither adoption nor erasure is automatic. A previously completed legacy revocation cannot be linked back to an email from its redacted receipt alone.

Operators can list pending revocations with `GET /admin/invites/revocations?limit=25` and pass the returned `nextCursor` as `after` for the next page. This Access-protected, read-only view contains operation IDs, phases and aggregate counts; it does not include account content or resolve a quarantine. Pagination is not a snapshot, so restart from the first page to see operations inserted before an earlier cursor.

For a pending operation, the [account inspection procedure](invite-revocation-inspection.md) lists verified Directory observations when all claim outcomes are known. It does not establish Vault ownership or quiescence and cannot resolve the quarantine.
