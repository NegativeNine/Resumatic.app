# Job seeker deployment and operations

This runbook covers the Google-only job seeker application. Repository implementation and local tests do not establish that a deployed service, model, payment or deletion audit has passed.

## Configure and provision

Production is the top-level `wrangler.jsonc` configuration. Staging is `env.staging`. Do not deploy production using `--env production`.

```sh
npm ci
npm run typecheck
npm test
node --test scripts/config.test.mjs
npm audit --audit-level=high
node scripts/setup.mjs staging
```

The setup command above prints a local plan. It makes no external request. After reviewing the configured account, bucket and gateway, an operator can use `scripts/setup.sh staging --apply --secrets`. `--apply` creates missing resources and updates the gateway to authenticated access, caching off and logging off. Existing resources are reused. The optional `--secrets` flag requires an interactive terminal and writes Worker secrets; values are never printed by the script. Run the corresponding production command only against the reviewed top-level configuration.

Before a staging deployment or live inference, run `node scripts/check-evaluation-secrets.mjs` with the staging Cloudflare account and a token permitted to list Worker secret names. It returns pending if names cannot be listed or if a secret shadows an evaluated model, extractor, or `ROLE_UNKNOWN_END_ENABLED` variable; it never prints Wrangler output or secret values. CI performs the same check. Never treat a 404, missing Worker, or permission error as an empty list. For first-time bootstrap, `scripts/setup.sh staging --apply --secrets` invokes interactive `wrangler secret put`; the pinned Wrangler version offers to create an inert draft Worker if the Worker does not yet exist. Confirm the intended account and draft creation in the terminal, then rerun the secret-name check before any application deployment or model call. Verify this behavior on the actual account; a failed or ambiguous bootstrap remains pending. Cloudflare documents that [secret changes create Worker versions](https://developers.cloudflare.com/workers/configuration/secrets/).

Set the real Google client, Access team/audience, Cloudflare account and gateway identifiers in the selected configuration. Store the session key, Google secret and model access token as Worker secrets. The staging-only `TEST_SIGNIN_KEY` must never exist in production. Verify the Google redirect URL against the deployed origin. The setup script also prints the GitHub environment secret names; Worker secrets and GitHub secrets are separate.

When connected apps are enabled, provision the `OAUTH_KV` namespace. Setup prints its identifier; place that identifier in the selected environment's binding. Configure `APP_ORIGIN` as an exact HTTPS origin, `MCP_ENABLED=true`, and the `global_fetch_strictly_public` compatibility flag. Configure `MCP_ALLOWED_ORIGINS` only for browser clients that need cross-origin MCP access; it is a comma-separated list of exact HTTPS origins. Native clients without an Origin header still work. Keep OAuth storage configured during deletion cleanup even if new connections are disabled.

```sh
node scripts/validate-config.mjs --environment staging --purpose deploy --report config-report.json
```

The preflight reports `ready` or `pending`; readiness is configuration evidence only. Gateway payload headers do not control every logging destination. Inspect gateway logs, Worker logs and any Logpush configuration using synthetic data before allowing real career uploads. Leave body collection and caching disabled. Model recordings must also contain synthetic data only.

Deployment and staging lifecycle preflight require a finite positive `DAILY_SPEND_CAP_USD` in the selected Worker configuration. The committed value is zero, so paid work remains disabled until the operator sets a cap. Bind all four per-Vault Workflows (`DISTILL`, `TAILOR`, `DOCUMENTS`, `REEMBED`). The public production workflow also refuses configured restore fences; maintenance deploys follow the fenced replacement procedure below.

## Billing configuration

Billing stays disabled unless `BILLING_ENABLED=true` and all required values are valid. Provide `APP_ORIGIN`, `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, an explicit `STRIPE_API_VERSION`, and `BILLING_PLANS_JSON`:

```json
{"free":{"generationLimit":3},"paid":[{"id":"pro","priceId":"price_REPLACE","generationLimit":50}]}
```

The numbers are an example deployment configuration, not a pricing decision. Use allowlisted recurring Stripe prices. `generationLimit` covers all generated outputs. There are no trials. An active subscription alone does not grant paid access: a settled invoice must establish the paid period. A scheduled cancellation preserves access through the paid end date; delinquency does not create a new quota period. Configure the Stripe portal for payment details and cancellation. Enable plan switching only after its proration and entitlement behavior has a separate tested policy.

Webhook verification uses the exact request body, all `v1` signatures and a five-minute timestamp window. Reconciliation uses current Stripe state; delivery timestamps do not order subscription events. Duplicate delivery must preserve the settled invoice and quota bucket. Validate checkout, cancellation, duplicate and reordered events in Stripe test mode, then attach evidence from one live payment and cancellation to the release gate.

Checkout keeps a durable server-generated intent and recovers a lost response by its Stripe metadata. Cancel a pending checkout before changing its plan. A confirmed expired session receives a fresh key; a creation with an unknown outcome older than 23 hours requires operator reconciliation and cannot start another payment. Resolve the original Stripe session and customer before clearing any intent. Account deletion expires open checkout sessions, cancels subscriptions and verifies their current state during both deletion sweeps; missing billing credentials or a remote failure keeps deletion pending.

Each Checkout creation also installs a durable Vault dispatch fence before contacting Stripe. A successful response records its exact session ID in the same transaction that settles the fence. Both deletion sweeps check those IDs directly, expire open sessions, and check and cancel any resulting subscriptions; they do not depend solely on list visibility. Account destruction and maintenance wait while creation is in flight; an error or interrupted response leaves a fence because the creation may still arrive later. Retrying does not clear an older uncertain attempt. Operator reconciliation must establish that all old requests can no longer create sessions and resolve any resulting payments before any fence is removed; there is currently no automated procedure that establishes this. This protection requires every deployed writer to use the fence, so mixed-version rollout, older checkout history and real Stripe behavior remain release gates.

Customer creation, including deletion's idempotent recovery request, uses the same kind of durable fence. The returned customer ID is persisted atomically when its own fence is settled, even if access was closed while Stripe was responding. Failed or interrupted creates remain fenced, including after a later successful retry. Existing or mixed-version customer creates did not install this fence; provider reconciliation and rollout verification remain necessary before relying on deletion evidence.

An unknown customer creation older than 23 hours also blocks automatic deletion recovery, because Stripe may have pruned its idempotency key. Locate the original customer in Stripe using `metadata.account_uid`, inspect all matches and resolve any duplicate customers or subscriptions. The Access-protected `POST /admin/vaults/:id/billing/customer` accepts `{ "customerId": "cus_..." }`; the server verifies the customer metadata against the Vault owner before recording it. This repair records one verified association, not proof that other matching Stripe customers were cleaned up. The operator must resolve all duplicates before accepting deletion evidence.

Stripe cleanup cancels future billing and expires pending payment links. It does not erase Stripe customer, invoice or payment records. Retention of those external records, Workflow history, gateway metadata and storage recovery history remains a separate review even after application-store counters reach zero. Keep the deletion acceptance check pending until that review states the applicable retained stores and windows.

## Live model and staging checks

Cloudflare catalog IDs are exact: the defaults use `anthropic/claude-haiku-5.5` and `anthropic/claude-sonnet-5.5`, not the hyphenated provider-native names. See Cloudflare's [Haiku](https://developers.cloudflare.com/ai/models/anthropic/claude-haiku-5.5/), [Sonnet](https://developers.cloudflare.com/ai/models/anthropic/claude-sonnet-5.5/) and [catalog lookup](https://developers.cloudflare.com/agents/models/ai-sdk/) documentation. The unified [chat completions endpoint](https://developers.cloudflare.com/ai-gateway/usage/rest-api/) accepts third-party models, but the Claude model pages show the native Messages request format; validate the actual gateway translation and JSON responses in the budgeted staging run. Local tests do not establish interoperability or schema compliance.

The default judge `openai/gpt-5` is scheduled for removal on December 11, 2026, according to [OpenAI's deprecation notice](https://developers.openai.com/api/docs/deprecations/). Choose and evaluate a replacement before that date. OpenAI recommends GPT-5.6 Sol, which [Cloudflare lists as Responses-only](https://developers.cloudflare.com/ai/models/openai/gpt-5.6-sol/), so it needs a Responses-format request rather than the existing Chat Completions format.

The shared model adapter has an **opt-in**, locally tested Responses path for `openai/gpt-5.6-sol`. It sends `store: false` and retains the gateway's payload-log and cache controls. It also requests OpenAI's `prompt_cache_options: { mode: "explicit" }` with no breakpoints to disable the provider's separate implicit prompt cache; [OpenAI documents this opt-out](https://developers.openai.com/api/docs/guides/prompt-caching/). Cloudflare's pass-through of this option has not been verified: confirm it and provider retention before processing career text. It is not the default judge: evaluate its output, failure handling, retention and latency through the configured gateway before selecting it. This model is intentionally absent from the built-in price table: its [Cloudflare pricing](https://developers.cloudflare.com/ai/models/openai/gpt-5.6-sol/) varies by input length and includes a separate cache-write rate, which the two-number table cannot represent exactly. Supply a current, conservative upper-bound override through `MODEL_PRICES_JSON` for the Worker and `EVAL_MODEL_PRICES` for evals, with the existing provider billing controls and daily price review. Local tests do not verify gateway compatibility, provider retention or final invoicing.

Model calls require explicit positive `EVAL_BUDGET_USD` and integer `EVAL_MAX_CALLS`. The Node model adapter reserves a conservative known-price bound before each HTTP attempt, including schema retries. Unknown prices require `EVAL_MODEL_PRICES` with input/output USD per million tokens. `CF_ACCOUNT_ID`, `CF_AI_TOKEN` and `AI_GATEWAY_ID` are also required. Missing configuration produces `pending` and no live calls.

Worker model accounting uses the configured price table for settlement. If the token counts needed by that table are missing, the attempt remains unknown with its reservation retained; it is not priced using a different built-in rate. A call with no output-token bound is refused before dispatch if its configured output price is positive. These safeguards do not establish provider billing bounds or make a per-vault reservation a provider-side hard cap.

The live CI evaluation and staging E2E jobs are deliberately blocked before their model calls: their budgets do not yet enforce one combined authorization. A deployed staging Worker therefore does not imply a passing E2E. The first-pilot runner keeps a persistent local ledger across extraction and tailoring, but its real shared-coordinator adapter is also blocked until the staging URL is proven to reach the Worker's account and ledger namespace and provider bounds are established. Its local ledger does not cover staging E2E or other hosts. Do not run the direct commands below, the E2E, or another host against the same authorization without accounting for all prior reservations and provider-side budget.

Before creating its one-shot local campaign marker, the first-pilot preflight checks that the shared ledger has enough remaining weighted calls for the minimum extraction and tailoring runs. This is a point-in-time feasibility check, not a reservation: concurrent consumers or actual model costs can still prevent a run from finishing.

A staging-only `PilotBudget` Durable Object and separately authenticated `/auth/test/pilot-budget/*` endpoints provide a shared, fixed-name ledger. Its secret, `PILOT_BUDGET_KEY`, must be at least 32 bytes and can be set interactively with `npx wrangler secret put PILOT_BUDGET_KEY --env staging`; never set it in production. Initialization fixes a maximum of $10 and 50 attempts (or smaller limits) and cannot reset usage. Reservations are nonrefundable, duplicate attempt IDs are refused, and reported unknown or excessive usage freezes the ledger. A crash can leave a charged reservation pending without automatically freezing it. The API accepts accounting metadata only, never prompts or responses.

Node evaluators and opt-in Worker pilot mode have reservation adapters, but **real pilot dispatch remains blocked in code** pending verified same-ledger identity and provider-side bounds. The Worker mode rejects conversion and Workers AI models, including `@cf/` IDs on chat routes, because their costs or hidden attempts are not bounded; ordinary non-pilot staging traffic bypasses this ledger. Browser Run Quick Actions are billed separately in [browser hours](https://developers.cloudflare.com/browser-run/pricing/) with billing-period rounding, and their cost is outside the model ledger. While `PILOT_SHARED_BUDGET=true`, an uncached PDF request fails before Browser Run; existing cached PDFs remain downloadable, and the preview and Word export do not invoke Browser Run. A privileged operator can also bypass the ledger through direct provider requests, storage deletion, or a different account or Durable Object namespace. A provider-side billing limit, verified cost and retry bounds, complete call coverage, and end-to-end staging validation remain required; keep the paid CI guard in place.

The staging-only identity diagnostic exercises the Node HTTPS endpoint and a selected real Worker model-attempt path against the same temporary coordinator record. **Do not trigger it until older Worker and Workflow versions and any in-flight work are proven unable to call providers.** The current HTTP Worker requires pilot mode before opening a challenge, but it cannot establish that an older Workflow uses that mode or contains its dispatch gate. In the current guarded code the matching model attempt deliberately fails before a provider call; use only a disposable synthetic staging account and expect its run to fail. Supply `STAGING_URL` and `PILOT_BUDGET_KEY` privately to the Node process. From the same `SharedPilotBudget` instance, call `beginIdentity(path, vaultId)`, trigger the corresponding synthetic run, poll `identityStatus(nonce)`, then call `consumeIdentity(nonce, expectedRunId)` within two minutes. `path` is one of `distill`, `tailor`, `document`, `reembed`, or `vault`. The selected path is checked against a label inside the actual model-call code, not accepted from the triggered request. The returned worker and runtime version IDs, path, run and step must be compared with the intended deployment and run; the challenge is single-use. Expiration, a different ledger, missing version metadata, or an uncertain response fails the diagnostic. Never put the key in logs, shell arguments, or Workflow state.

This proves only that the particular observed invocation and HTTPS endpoint reached the same coordinator object. It does not establish ownership of the intended Cloudflare account, unobserved paths or versions, in-flight Workflow version behavior after deployment, provider billing bounds, or safety of ordinary staging traffic. Cloudflare documents [version metadata bindings](https://developers.cloudflare.com/workers/runtime-apis/bindings/version-metadata/) and [Workflow bindings](https://developers.cloudflare.com/workers/runtime-apis/bindings/), but Workflow version metadata semantics for in-flight runs must be verified on staging. Local tests exercise the real coordinator and invoke the Distill, Tailor, Document, Reembed and Vault method code with stubbed Vault, R2 and Workflow steps; they check that each observation occurs before a provider call. These direct method tests do not reproduce the deployed runtime or prove binding identity. All five paths require separate staging evidence. The diagnostic does not change either code-level readiness gate.

Production release checking remains blocked in code while historical-version and share handling and verified manual edits require further validation. An operator evidence flag cannot clear this implementation blocker; see the release status for the affected paths.

Conversion-quality warnings are heuristics, not a determination that a file was read correctly. Cloudflare's documented Markdown conversion response does not provide a PDF page count, so ordinary PDF page counts remain unknown. OCR sources record the number of page images actually submitted, not a claim about the original PDF's total pages; sparse-text checks can use that known image count. Calibrate the thresholds with the real dataset before relying on them for format-specific decisions.

Use the extraction CLI's offline mode for harness development; it is not a model-quality result. Keep real consenting-user fixtures outside Git. Promotion reports must name model IDs, prompt hashes, split and repetition count. Held-out promotion results cannot be replaced by development results or hand-picked examples.

Extraction retains the full source line for non-skill facts and merges proposals on the same line and role. LinkedIn skills use parser-identified CSV cells. These conservative rules can miss skills in other layouts and merge distinct facts; their English qualifier checks do not prove meaning or cover all languages or multiline context. Measure their effect and audit unsupported claims on the held-out dataset before promotion.

The staging E2E requires `STAGING_URL`, `TEST_SIGNIN_KEY`, and explicit positive `EVAL_BUDGET_USD` and `EVAL_MAX_CALLS`. Before model calls it freezes those lifetime limits in the synthetic test Vault; the independently configured daily cap also applies. The run fails closed if the test-only budget endpoint is unavailable. The E2E records the Vault run ledger before deletion and distinguishes account access revocation from storage erasure. An upload whose acknowledged R2 put finishes after Vault closure is deleted when the Vault authoritatively rejects completion as gone; ambiguous RPC failures retain the key to protect already-committed sources. This cleanup is best effort: a Worker crash or unknown R2 outcome can leave a late write, so it does not prove quiescence. The audit additionally needs Access service-token credentials. Its Workflow probe checks every supplied ledger ID, including superseded attempts, but cannot independently prove that the captured inventory is complete. Therefore, even all-zero counters remain pending until an independent complete-inventory attestation exists; missing counters, an unavailable endpoint, or an incomplete retention review also remain pending.

The Vault authenticates the session and atomically records a deletion intent, closes normal access, and schedules a recovery alarm before the Worker calls the Directory. This orders deletion against sign-out everywhere. If the Worker stops before that call, the Vault alarm schedules another retry before contacting the Directory, then uses its persisted owner and Vault ID; the Directory verifies that ID against its current account record. The Vault removes its retry after Directory acknowledges a durable cleanup alarm. A scheduling failure rolls back the intent. After an intent is committed, the same session can retry deletion even if a control-plane failure returns an error, while ordinary API access remains closed. The Directory commits its deleting state and an alarm in one SQLite-backed storage transaction, quiesces the Vault, and the Worker confirms quiescence before returning HTTP 202. Directory alarm handlers also arm a retry before external calls; an extra idle alarm may run after cleanup. When no earlier alarm exists, retries and cleanup are scheduled for 60 seconds later; platform delays can make them later. Only one alarm handler runs per object at a time: a pre-armed retry does not by itself resolve a permanently stalled call, and in-flight timeout and termination behavior still needs staging verification. An acknowledgement lost after the Vault closed can make the old session unusable for ordinary access even though deletion returned an error. Alarm retries also quiesce before checking an unresolved initialization marker. Those markers and the Workflow dispatch fences still prevent destruction; access revocation does not certify erasure. Verify the storage transaction, retry, rollout and mixed-version assumptions on staging before relying on them in production; older Worker and Vault versions do not enforce the intent protocol.

An operator can compare a synthetic E2E manifest with currently visible provider instances using `node scripts/compare-workflow-inventory.mjs --environment staging --manifest deletion-manifest.json --max-instances 250 --report provider-inventory.json`. Configure `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_API_TOKEN`, and `STAGING_URL`; the configured account and manifest origin must match. Use a narrowly scoped read-only token and do not put credentials in the manifest or command line. This read-only diagnostic lists all visible instances of the four per-vault Workflows and fetches each instance's simple metadata, including its parameters, to attribute instances to the vault. It makes up to one detail request per visible instance and stops at the explicit bound. Provider responses may transiently include other users' data in memory; the report contains only IDs, counts and fixed codes, with no payloads. An unattributed instance, missing ledger ID, unexpected instance or parameter mismatch needs review. Cloudflare's [list](https://developers.cloudflare.com/api/resources/workflows/subresources/instances/methods/list/) and [detail](https://developers.cloudflare.com/api/resources/workflows/subresources/instances/methods/get/) APIs do not establish a complete, quiescent snapshot. Results always remain pending: they do not settle unknown creates, inspect fleet Workflow step state, prove retention expiry or clear any deletion fence. Fleet re-embedding steps can themselves retain vault and run IDs, so include them in the retention and erasure review.

Workflow dispatch is fenced before external creation so closing or moving a vault waits for acknowledged in-flight creates. A rejected or interrupted create has an unknown outcome; a missing or terminal instance observed once does not establish that a delayed create cannot still arrive. For an open vault with a starting run, the alarm can retry creation with the same instance ID at most three times with persisted backoff. Before the first retry it installs a separate permanent uncertainty fence. Neither a successful retry, a duplicate response, nor an acknowledgement from the original call clears that fence. A SQLite trigger also prevents older unconditional cleanup from deleting the original marker while the retry fence exists. These protections require deployed validation; older code may bypass them, so do not rely on mixed-version recovery without proving old instances have drained.

The retry can restore work but does not resolve erasure, move or cancellation. Deletion and maintenance remain pending while any marker exists, and cancellation remains pending even if one lookup reports the instance absent or terminal. The migration conservatively marks every historical Workflow run and legacy source/resume run ID, including terminal runs; affected accounts require a future provider-verified reconciliation procedure before deletion or transfer can finish. No operator override exists today. The application reports an unconfirmed start after 30 seconds while a starting run retains a marker. Initial dispatch schedules an alarm before creation, but an interruption during alarm scheduling can still leave a marker requiring operator attention. Retrying may lead to additional provider processing or model attempts; local attempt reservations enforce configured application spend limits but do not guarantee a provider invoice ceiling or that a model is called only once. Confirm same-ID uniqueness, post-create visibility, billing controls and mixed-version behavior against the live provider before rollout, and keep Workflow inventory and erasure audits pending.

Directory initialization attempts are also fenced before cross-object calls, and account state is rechecked after acknowledgement. A sign-in or replacement preparation can retry initialization for the same persisted vault and owner after an unknown outcome; concurrent attempts share one call. The earlier attempt's marker becomes permanently sticky before a retry, and an acknowledgement from this code does not clear it. A SQLite trigger also prevents an older unconditional delete from removing a sticky marker; it is verified locally and must be tested on the deployed platform. Older code may bypass the fence altogether, so do not rely on recovery across a mixed-version deployment without first proving older instances have drained. This may restore access but deletion or transfer remains blocked until a provider-verified reconciliation procedure exists. The migration conservatively fences **all** existing vaults, replacement targets and retired vaults. Historical orphaned attempts whose Directory rows have already been removed cannot be inventoried by this migration. Any future partial-erasure path also needs a durable checkpoint for a crash between `destroy()` and the Directory's state update; treating an empty vault as closed without that evidence can hide a late initialization. These limits remain release blockers.

Workflow calls must identify an existing run with the correct kind and target. Calls from older in-flight Workflow code that lack this identity, or refer to legacy rows without a run ledger, fail closed even when a previously completed step is replayed. Such interrupted work needs a fresh run after reconciliation; upgrading the Worker alone does not migrate an in-flight execution or resolve its dispatch fence. Preserve old deployments until a staged upgrade and recovery plan has been verified.

## Metrics, alerts and abuse limits

Bind `METRICS` to the selected Analytics Engine dataset and use `METRICS_DATASET` for alert queries. Workflow metrics use `blob1..5` for run ID, step, route, model and outcome; `double1..4` for milliseconds, input tokens, output tokens and integer micro-USD. HTTP metrics use step `http` and a bounded route category. Neither shape contains career text, filenames, IP addresses, raw URLs or credentials.

Completed-run latency uses a separate `run_total` event. The dashboard aggregates end-to-end p50/p95 by run kind and model-attempt p50/p95 by route and model. Alert and cost queries exclude `run_total` so totals do not count model work twice. Unknown cost remains visible instead of being reported as zero. Verify these query shapes against the deployed dataset before accepting latency or spend evidence.

To enable the fifteen-minute alert job, set `ALERTS_ENABLED=true`, `CF_ANALYTICS_TOKEN` with Account Analytics Read, `ALERT_WEBHOOK_URL`, and `ALERT_SPEND_USD_PER_15M`. Optional thresholds are `ALERT_FAILURE_RATE` and `ALERT_HTTP_5XX_RATE` (defaults 0.05), and `ALERT_MIN_ATTEMPTS` (default 20). Unknown model cost raises a separate alert. The webhook receives only window totals and error-category codes. Disabled alerts make no network request. Alerts can repeat while a threshold remains breached; operational acknowledgement belongs in the configured receiver.

Queries weight rows by `_sample_interval`; these are sampled operational measurements, not a billing ledger. Quota and spend reservations in the Vault remain authoritative. The profile, role, and fact reads retry at most twice on transient retryable Durable Object errors, recreating the stub each time; overloaded errors are never retried. The `AUTH_LIMIT` and `WRITE_LIMIT` bindings limit bursts per Cloudflare location. Authenticated writes use the user ID; guest authentication/OAuth requests use an HMAC of the IP address. Shared networks can still hit a guest limit. Missing optional bindings skip burst protection, so configure them before public launch.

## Interview answer provenance

Answers to generated experience questions are saved as confirmed user-authored facts, without consuming an output credit. The vault also retains the originating question and the exact original answer as history. Editing the fact changes the claim used for generation; the original answer remains visible as history and is never used to override the correction. Interview provenance is included in the owner's data export and fenced replacement transfer, excluded from coach shares and MCP tools, and removed with the vault.

`GET /api/export/archive` streams a ZIP containing `vault.json` and the source objects referenced by that snapshot. It accepts at most 128 source records and 100 MiB of member data, plus ZIP overhead. The JSON snapshot is assembled before streaming, so a large vault may reach Worker memory or RPC limits before the archive limit is checked. Source objects are checked by ETag; a missing or changed object, interrupted connection, or failed session check during streaming errors the download rather than completing a partial ZIP. Session checks cannot recall bytes already delivered. Verify streaming and deletion races against deployed R2 before relying on those checks. The existing JSON export and individual source downloads remain available for vaults over the archive limits.

This is not Browser Run evidence or an ATS parser assessment and cannot satisfy the release gate.

For extraction, copy the complete JSON object returned by the final audited `--promote` assessment into `extraction.promotion`. It must have `mode: "human-audited"`, `profile: "full"`, a winner, no pending ranking, and an eligible winning result with at least 15 held-out cases, 50 distinct audit sample keys, at least 50 reviewed facts and priced usage. The release check verifies that every eligible result has ranking metrics and that the winner has the lowest review cost, with price and p95 latency as tie-breakers. This checks the attested aggregate, not the authenticity of the underlying dataset or audit. The top-level extraction measurements must exactly match that winning result. Supply `extraction.priceOverrides` as the same model-price override object used by the evaluation, or `{}` if none was used. The release check recomputes the configuration hash from the current checkout using the promotion's tested environment and those overrides; it also checks that the production model IDs match the tested IDs and every configured default, format or experiment extractor is an eligible strategy in that assessment. A staging assessment is acceptable when these checks pass. The `full` assessment separately requires a 40-case dataset with at least 20 synthetic and 20 consented real cases, independent labeling, and review of judge/human disagreements. A Round 1 or exploratory pilot report cannot satisfy the release gate.

The standalone strategy assessment measures PDF/DOCX converted text. Its aggregate eligibility does not establish the quality or grounding of LinkedIn import, OCR transcription, or a particular format-specific route. Keep those routes pending until their own end-to-end cases have been evaluated and reviewed; changing their implementation invalidates the configuration hash but a matching hash alone is not route-specific quality evidence.

`node scripts/check-release.mjs` validates the evidence envelope, copied aggregate and checked-in extraction configuration; it does not fetch or authenticate linked reports or independently certify the dataset, price overrides or human attestations. The reviewer must inspect those reports, the actual deployed configuration, sample adequacy and retention conclusions. Before deployment, the workflow allows only these production Worker secret names: `SESSION_KEY`, `OIDC_CLIENT_SECRET`, `CF_AI_TOKEN`, `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `ALERT_WEBHOOK_URL` and `CF_ANALYTICS_TOKEN`. It also rejects any allowed secret that shadows a checked-in production variable. New secret names require a reviewed change to `scripts/lib/release-secret-names.mjs` and this list; place non-secret settings in the reviewed configuration. This check cannot prevent an out-of-band configuration change after it runs.

The billing fields are operator attestations and do not independently verify Stripe transactions; the linked report must substantiate the test-mode flow, live payment and cancellation. The deletion audit currently cannot prove its Workflow inventory complete. The release check shares that audit capability and remains pending with `DELETION_INVENTORY_AUDIT_UNAVAILABLE` even if deletion is marked passed. Resolving this requires an implemented, independently verifiable complete-inventory audit and its review, not an environment flag or a manually edited status.

## Fenced vault replacement

`scripts/move-vault.mjs --source <vault-id> --operation <stable-operation-id>` prepares a replacement and exits pending with both IDs. Deploy `RESTORE_FENCE_IDS` containing both the source and replacement before rerunning the same command with `--copy-and-cutover`. Both requests require `APP_ORIGIN` and Access service-token credentials. The script streams checksum-verified pages directly between the protected endpoints; it does not write career text to local files. The server applies current security, billing and usage checkpoints, copies R2 and then swaps the Directory pointer. Keep the source fenced through its deletion audit and the replacement fenced through verification. A retry uses the same operation ID. There is no direct production SQLite rewind in this workflow; never use an old snapshot to revive revoked credentials or a deleted account.

Maintenance endpoints and the move and deletion-audit scripts canonicalize hexadecimal vault IDs to lowercase. Fence configuration matches whole IDs case-insensitively. This does not make the deletion inventory complete or establish R2 quiescence.

## Uploads and embedding rebuilds

Upload reservations persist the metadata/body digest and a unique R2 key before writing bytes. Retries recover the same source; conflicting metadata fails before replacing an object. Uncertain writes retain their reservation, and cleanup first permanently expires a pending intent. If an acknowledged put completes after the expiry sweep, the Worker checks that its exact reservation is permanently expired before deleting that key again; a failed check or a generic conflict alone does not authorize deletion. This is best effort: a crash or a different in-flight put can still leave a late object. Validate interrupted upload and deletion races against staging R2 before accepting this as live evidence.

An experimental `R2_CACHE_FENCE_ENABLED=true` setting is gated by staging-style configuration and bindings. It records a marker before each new PDF or DOCX cache put, settles it only after an observed acknowledgement, and blocks vault destruction and replacement while a marker remains. At 64 unresolved attempts per vault, new cache puts are refused before dispatch; existing markers remain. `GET /admin/vaults/:id/cache-write-fences` reports metadata for unresolved attempts. New markers contain a SHA-256 digest of the object key, and the put carries an opaque attempt ID in [R2 custom metadata](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/); older markers have no digest. These are correlation hints only: a later put can overwrite metadata and an unseen request can still arrive, so a head or list result cannot settle a marker or prove quiescence. An interrupted call may leave a marker with no automated clearing procedure. Before enabling this even for a staging drill, review provider semantics and how such a marker can be resolved, and ensure older writers are quiescent. Production preflight rejects the setting; the runtime gate depends on configuration and is not an intrinsic environment boundary, so do not bypass preflight. Uploads, transfers and older writers are outside this experimental fence, so it does not establish erasure.

`GET /admin/vaults/:id/cache-write-correlation` is an Access-protected, read-only aid for comparing those digests with current export objects. It scans at most two pages of 100 objects and performs at most 16 object heads; its response omits object keys, filenames and arbitrary metadata, and always remains `pending`. A limited or unavailable scan is not an inventory, and even an exhausted scan and matching metadata are only observations taken at different times. Cloudflare says a [negative R2 read does not wait for or cancel an earlier in-flight put](https://developers.cloudflare.com/r2/reference/consistency/). [R2 Data Access Logs](https://developers.cloudflare.com/r2/buckets/data-access-logs/) are asynchronous and best effort, and can omit events, so missing logs cannot establish that a put failed. Do not clear a marker or conclude erasure from this diagnostic, object metadata, logs or a time delay.

An R2 sentinel does not recover these existing writes: they are unconditional, so a delayed write can overwrite it. For a future protocol, a unique per-attempt object initialized with an acknowledged random placeholder could require every data put to match that placeholder's ETag. Deleting it would fence a delayed conditional data put only if nothing can recreate the matching placeholder and all earlier data-bearing writers used that exact condition. An uncertain initial placeholder put can itself arrive after the sweep and leave an object under the prefix, however, so this does not meet the current empty-prefix erasure requirement. A create-only data put blocked by a sentinel can also succeed after the sentinel is deleted. Cloudflare documents [atomic evaluation of conditional writes at commit](https://developers.cloudflare.com/r2/reference/consistency/); the local conditional-put diagnostic models these orderings, but does not establish provider quiescence. A safe recovery needs a provider-backed resolution of all in-flight requests or an explicitly revised storage and erasure contract, and must also handle older unconditional writers.

**Multipart candidate for future deletion fencing, not implemented:** use a separate multipart upload for every write attempt, including uploads, OCR inputs, export caches and replacement copies. Create the upload without sending user data, then atomically register its returned upload ID and target key in the open Vault before sending any parts or a completion request. Closing the Vault stops new registrations; deletion must retain its ledger while aborting every registered upload, then sweep the prefix only after every abort or completion has a conclusively safe outcome. A create response that arrives after closure cannot authorize parts or completion. Retries need distinct registered upload IDs; neither a missing object nor a lost response settles an attempt.

This could make registered writes revocable without keeping an object sentinel, but it is not an erasure proof. Before implementation, obtain Cloudflare confirmation that abort and complete for the same upload have a definitive ordering: after a successful abort, or a definitive already-completed/aborted result, no previously dispatched completion can publish an object after the following sweep. Establish which provider responses actually prove that result; an ambiguous failure is not enough. Also establish how to remove parts whose uploads were already in flight at abort and prove their removal. The [Workers API](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/) documents successful abort and completion, not these race guarantees. A create whose response is lost can leave an unregistered, empty multipart upload; even if it cannot contain career text under this protocol, its key and metadata can persist, and a late create can appear after an inventory. The same API reference says uncompleted uploads are automatically aborted after seven days; that does not establish part erasure, storage retention or a complete inventory. Confirm cleanup and retention separately. Prove a rollout drains all old unconditional writers and their in-flight writes before relying on the new ledger, and migrate all write paths without an unfenced fallback. Until those guarantees, recovery procedures, mixed-version behavior and staging tests are established, deletion and replacement remain pending.

Embedding rebuilds stage vectors per Vault while serving the previous generation, then activate only a complete generation. Fleet dispatch must use stable run IDs, bounded batches and the same model-budget reservations; failures stay resumable. Run a small staging canary and verify generation activation, cancellation and account deletion before starting a fleet rebuild. Rebuilding embeddings is a paid model operation and needs an explicit configured budget.

## Directory capacity rollout

**Do not roll out shard changes yet.** A pending new-account placement can outlive deletion and create a second account on its old shard. The normal rollout also needs older Worker versions drained. Existing global user IDs remain global; new shard-prefixed user IDs permanently identify their home. Returning `DIRECTORY_SHARDS` to `1` disables placement of new users into shards; it does not move existing users. Admin listings must still query all seventeen Directory objects after rollback. Do not change the fixed shard count to a different number.

The production deployment workflow rejects sharded placement in the checked-in configuration and rejects a `DIRECTORY_SHARDS` Worker secret, whose value it cannot inspect. Remove any such production secret and use the checked-in configuration before deploying. This guard does not prevent out-of-band deployments or resolve pending requests and existing sharded users.

The global Directory now checks a deletion epoch captured before issuing Google OAuth state. Deletion and Google identity removal advance the epoch; the migration installs SQLite guards atomically to reject legacy global creation, home-claim and binding writes once active. `test/integration/global-auth-fence.test.ts` exercises the previously failing global public-registration interleaving with a synthetic identity. It does not test Google, browser cookies, or deployed mixed-version traffic. This does not fence already-dispatched sharded creates, nor requests served by old code before the global object migrates. Establish a provider-verified deployment and in-flight writer drain before relying on the fence.

A migrated sharded Google deletion now releases the home through a versioned coordinator RPC that advances the same epoch in the release transaction. A shard-local pending/acknowledged outbox survives retries and is removed with the identity. A lost acknowledgement can cause another conservative epoch advance; migrated SQLite guards reject legacy Google home and identity deletion without their transaction markers. These guards do not constrain old code before its object migrates or a creation already dispatched to a shard. Verify rollout, migration and drain before relying on them.

The epoch is global: any global account deletion or sharded home release can invalidate unrelated pending Google sign-ins, and the user must restart sign-in. A deletion between a sharded account creation and home binding can leave an active shard account and an unbound global identity-home claim. A fresh sign-in recovers the same account, but abandoned claims have no proven safe automatic cleanup; account deletion and retention acceptance remain pending.

Production deployment preflight requires the reviewed configuration to set `INVITE_ONLY` to the exact string `"true"` and rejects an opaque Worker secret of that name. This reduces exposure to the demonstrated public-registration path, but invitation changes, already-dispatched calls, mixed Worker versions and other deletion races still need resolution. Invite-only mode is not proof of safe deletion, and out-of-band deployments can bypass preflight.

For current code, a new invited account's global home claim rechecks the verified email and writes or reads the claim in one Durable Object operation. A prior invite check alone cannot authorize a claim after the invite was revoked. Older Worker versions do not supply the email, so their new invited-account claims fail closed during a mixed-version rollout; existing accounts are still routed directly. This does not cancel target creation already dispatched after a claim, and older Directory versions do not enforce the recheck. Both remain rollout blockers.

The isolated local diagnostic holds an unregistered creation route, deletes that identity, changes the shard setting, creates a replacement, then resumes the old route. Run it explicitly:

```sh
RESUMATIC_PLACEMENT_DIAGNOSTIC=1 npx vitest run --project integration test/diagnostics/placement.diagnostic.ts
```

It currently exits nonzero: two local Durable Objects contain accounts for the same synthetic identity when one was expected. It contacts no model or other external provider. Ordinary CI does not run it. A future fix must make the invariant pass, including interrupted dispatch and deletion cases; one passing diagnostic does not by itself establish rollout safety.

An experimental `PLACEMENT_FENCE_ENABLED=true` path is disabled by default, rejected by production preflight and restricted to disposable `test` identities under `@placement.invalid` with staging-style bindings. It reads a coordinator-wide epoch before identity lookups, then registers a generation and attempt only if that epoch is still current; target tombstones reject delayed registered attempts. Releasing a synthetic claim advances the epoch in the same transaction, so a reservation carrying an earlier observed epoch fails closed. This also makes unrelated synthetic sign-ins holding that earlier epoch retry. Deletion closes that generation, seals its registered attempts, removes the target identity, and uses a durable outbox and release receipt to finish the global claim removal after interrupted responses. `POST /admin/placement/reconcile` seals known attempts, and `/admin/placement/inspect` plus `/admin/placement/cleanup-orphan` support generation-qualified cleanup of an unbound synthetic claim. Cleanup closes registration first and retains a claim if sealing reveals an account. These endpoints require Access and accept synthetic subjects in JSON bodies only. Opaque attempt tombstones and generation release receipts persist indefinitely; their retention and provider behavior require review.

This prototype does **not** settle an epoch-read RPC that itself arrives after deletion. A pre-deletion sign-in whose first coordinator read is delayed can receive the new epoch and create a new generation. A sharded target request already authorized and claimed before invite revocation can likewise arrive after deletion. Two additional opt-in diagnostics demonstrate those gaps:

```sh
RESUMATIC_PLACEMENT_DIAGNOSTIC=1 npx vitest run --project integration test/diagnostics/pre-reservation.diagnostic.ts
```

Both currently exit nonzero on the desired invariants. Pre-migration and mixed-version requests may not honor the experimental fence at all. Do not enable this for real identities or roll out sharding until a complete protocol, an operable legacy recovery procedure, retention review and staging evidence address those gaps. A passing test for registered attempts alone is not sufficient.

### Extraction experiment feedback

`GET /admin/vaults/:id/extraction-feedback` returns one metadata-only record for each source whose observation began after the feedback migration. It reports the extractor and counts of proposed facts, facts ever confirmed, rejected or edited during the seven days after the source was created, and user-added facts in that period. The confirmation, rejection and edit counts can overlap when a user changes a decision. A manually added fact is attributed once to the most recent observed upload within seven days; this association measures timing, not causation. `windowComplete` identifies sources whose seven-day observation has finished. Existing sources are deliberately not backfilled because their original review timestamps are unknown. The feedback ledger is copied with a fenced vault replacement and erased with the vault.
