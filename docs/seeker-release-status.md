# Job seeker implementation and release status

The roadmap separates repository delivery from real-service acceptance. The current work adds executable code and local regression coverage; no production deployment, model purchase, Google live sign-in, Stripe charge, external security assessment or beta observation period is implied by this document.

Tagging's caps come from arithmetic, not from measurement: 20 jobs and 120 facts an upload, 3,000 words looked through, four candidates a job and six a fact, eight occupation profiles and 120 questions to the judge. Whatever is over one is left untagged, which means unknown, and is counted. A candidate the judge declined leaves no row, so it is asked about again when the same upload is read again or the same line is uploaded again; keeping the questions asked would need a table of its own. Nothing before the judge looks for a hedge, a denial or an intention in a line, so that a label a line only mentions, denies or intends is not tagged rests on the judge alone, and no local test shows the real judge declines one. The stage's reads of the taxonomy have run only against the local D1 stand-in. A line marked sensitive while the stage runs is in no judge call sent after the mark and keeps no tag, but its words may already have been looked up in the taxonomy's database or be in a call under way.

The supervised pilot ledger admits only one unresolved model attempt at a time and checks stored attempt totals before accepting a reservation or reporting healthy status. Concurrent contention may stop an exploratory run. The Node evaluation adapter now asks a typed-decision judge as the Worker does, and sends its typed decisions for the judge and for ranking one at a time, so it no longer contends with itself there. A typed-decision judge is one request for each fact or line, so with staging's judge the first pilot needs at least 66 weighted attempts and its preflight refuses to start within the 50 authorized. Whether to authorize more, or to use a smaller case, is not decided. These local checks do not establish mixed-version behavior, complete provider accounting or a hard provider-side spend bound.

The first staging pilot now checks the named AI Gateway's Logpush and OTEL settings before creating its campaign marker. This is a point-in-time prerequisite, not a complete privacy audit or a guard on ordinary production traffic: account-level exports, settings changes and provider retention still need review. Cloudflare states that [Logpush ignores per-request log suppression headers](https://developers.cloudflare.com/ai-gateway/observability/logging/logpush/) and that [OTEL spans can contain prompts and completions](https://developers.cloudflare.com/ai-gateway/observability/otel-integration/).

Billing reconciliation defers failed inbox events and revision-bound entitlement deliveries so a full batch of failures does not permanently starve newer work. Vault alarms schedule retries before upload cleanup and Workflow status I/O. Signed Google and Access tokens are checked for their not-before time with the existing clock-skew allowance. These safeguards have local tests; staging and provider behavior remain unverified.

When live progress is unavailable, the web app continues polling a known running source, resume or document after transient read errors, with bounded backoff. A successful terminal read, a non-retryable HTTP error or a session-ending error stops the poll; an explicit retry can reload the resource. The browser check uses synthetic responses, so deployed WebSocket and polling behavior still need validation.

Billing account state now carries a trigger-updated token, so current reconciliation and delivery acknowledgements detect an account that changed and returned to the same values or was deleted and recreated while provider I/O was in flight. A non-identifying global clock detects a missing account that was inserted and removed; it can also cause conservative retries after unrelated billing changes. Older in-flight code and plan delivery RPCs still need a mixed-version rollout and staging review.

Billing events now receive an opaque incarnation ID before reconciliation performs provider I/O. Conditional attribution, retry and deletion writes check that ID and the expected owner, so a stale response cannot alter a deleted and recreated event even if its visible fields and timestamp match. Legacy null IDs are assigned before dispatch; older running code can still issue unguarded writes and needs a rollout drain. The Directory also begins deletion work while a billing inbox request is in flight, so an unrelated stalled Stripe read does not prevent a provisional R2 sweep. The alarm still awaits billing and existing erasure fences remain in force. These changes need mixed-version and deployed race testing.

Deletion checks Checkout Session and subscription ownership before changing either. A session that completes during expiry is reconciled directly even if the subscription list has not caught up. Completed payment or subscription sessions with unpaid or unknown payment status remain pending while other known subscriptions are canceled. These checks do not establish a complete Stripe inventory or settle every invoice or provider-retention obligation; validate those separately against Stripe.

When a billing update creates a free quota bucket, the Vault imports the current month's legacy usage in the same transaction. For an unambiguous import with no newer ledger history, it records the in-flight legacy resumes and refunds their imported charges once if they fail. New-ledger failures no longer decrement the old counter. Already-created buckets, inconsistent counts and accounts with newer ledger history remain ambiguous and need reconciliation; the code does not guess which historical charges to refund. Local tests do not establish live Stripe delivery or quota behavior.

Replacement cutover schedules redelivery of the current plan in the same transaction that publishes the target Vault. A late acknowledgement from the old Vault cannot mark that delivery complete for the target. This requires the current Directory implementation; mixed-version rollout and real Stripe and replacement drills remain unverified.

The current webhook passes Stripe's customer account ID to the selected Directory, which records it with each new billing event only while that account is active. Reconciliation refuses to move an already attributed event if the customer's metadata changes. A delayed call from a current Worker therefore cannot create a new event after the account starts deleting; an older caller is rejected by current Directory code and must retry. Older Directory versions can still accept unattributed events, and existing customer-only events still need separate attribution and cleanup. Validate rollout, webhook retries and billing behavior against Stripe before relying on this change.

Connected-app generation rechecks its local grant after Workflow reconciliation and before creating a run. Resume delivery also rechecks after its awaited lookups; a revoked grant cannot use an already-started lookup to obtain the resume or create a new generation. A run committed before revocation may still dispatch and finish, and a response delivered before revocation cannot be recalled. Deployed OAuth and client behavior still require verification.

Coach-share creation reads the selected facts, roles and resume versions and creates the grant in one Vault transaction. A role edit or rejection cannot be interleaved between those reads and the grant. Existing grants remain immutable snapshots, and a response delivered before revocation cannot be recalled.

Coach accounts are ordinary accounts matched by the address they sign in with. The app sends no email, so the owner tells their coach which address they named and sends the link themselves, and a coach without an account still needs an invitation while sign-up is gated. Sessions issued before this change carry no address: their holders are told to sign out and in again before they can act as a coach, and nothing else about those sessions changes. Local tests use the development sign-in and synthetic accounts; they do not establish that a real provider's address claim matches what an owner would type (case, dots or aliases at the provider are compared exactly after lower-casing). An entry in a coach's client list is cleared by the Vault's alarm thirty days after its copy's last day; local tests run that alarm by hand and do not establish when a deployed alarm fires.

The app sends no email: an owner learns of a comment from a count when the app next loads, and a coach of a reply when they next open the copy. Signing out everywhere on the owner's account closes neither a shared copy nor its comments; revoking the link does. Local tests use synthetic accounts and stand-in models: they show a comment absent from every prompt those stand-ins were sent, which is not a reading of what a real provider receives. They render the page without layout, so where the comments sit beside the copy, and how a chosen line is marked, have not been seen in a browser.

The coach-share page keeps a link token in memory after a temporary exchange failure so the recipient can retry without putting it back in the address bar. It discards the token after a successful exchange or terminal rejection; a failed snapshot read can be retried using the session cookie. After the exchange the address names the copy by its grant ID, and each copy has a session cookie of its own, so a reader with several copies open reloads the right one. Local browser checks use synthetic responses and do not establish deployed link or cookie behavior.

A fact can be marked sensitive, together with every fact that has the same words. The mark is read in three places: where facts are chosen for anything generated, at each step and each model reservation of a run already in flight, and at the gates a resume, a letter and a shared copy pass before they are sent out. No stored resume, document or copy is rewritten, so unmarking makes each of them available again as it was; a run the mark stopped stays failed, with its credit returned. Local tests record what the stand-in models were sent after a mark and read every outward surface (`test/integration/sensitive-facts.test.ts`, `test/integration/outward.ts`). They do not establish what a real provider received from a call already under way when the mark landed. The upload itself is still sent whole when it is read again, and the embedding model still receives a marked fact's words on an edit or an index rebuild. The same line worded differently in another upload is not marked, and neither are different words for the same thing. A copy or a resume made from a fact that was later reworded is judged by that fact's mark, not by whether its old words are marked on another fact. The migration that adds the column has run only locally, and only the integrated order (preferences, sensitive facts, comments, suggested wording) is to be deployed.

To the coach a copy names, a copy closed by a mark is a copy that has ended: it does not open from their list, it is listed there as ended with none of its counts, and it can't be taken up, each in the words any ended copy gets. That it was closed for a while is not hidden: a reader or coach who looks again after the fact is unmarked finds the copy open, which a link that has expired or been revoked never is.

Work made while a mark stood is not always as it was once the mark is gone. A fact read from the same line as a marked fact is used with its own words as its only evidence while the mark stands and with its whole line afterwards, and work is compared with a fact's evidence exactly. A run in flight that cites or prints such a fact fails when the mark is removed. A line of an older version under review that was checked against such a fact while the mark stood no longer counts as checked after the unmark and has to be checked again, at one more output; marking the fact again makes the earlier check count again. A resume finished while the mark stood that prints such a fact as a skill and also cites it in a line can't have that line reworded after the unmark until the skill is taken off or a new resume is tailored. The last two are pinned as they are (`test/unit/sensitive.test.ts`, `test/integration/sensitive-facts.test.ts`). Whether a check made against a fact's own words should stand once its line is back in use is not decided.

**R2 erasure remains unproven:** current source uploads and replacement-copy writes record a separate durable marker before each R2 put. Source and OCR puts run inside the Vault, which clears only the acknowledged attempt's marker without a separate Worker settlement RPC; uncertain attempts hold deletion pending. New source markers are linked to their reservation so unrelated expired uploads can still be cleaned; old or unattributed source markers block all such cleanup. A crash before dispatch or an unknown R2 outcome can leave an unresolved marker, and no automatic recovery is claimed. Older deployed writers can bypass this fence and remain in flight while deletion sweeps run. Current PDF and DOCX routes store newly rendered caches in the Vault instead of writing R2. They no longer serve unbound historical cache entries; those objects remain subject to deletion sweeps. Before relying on erasure, establish provider-confirmed quiescence for previously deployed and unfenced writers and implement an operable recovery procedure for unresolved writes; a time delay or an empty prefix listing alone is not proof.

New PDF and DOCX cache entries use owner-checked Vault SQLite storage with per-item and aggregate limits, bounded chunks and eviction. Their keys include a hash of the complete checked render snapshot and a renderer version, so old unbound cache entries are ignored and regenerated. Oversized exports are served without caching; replacements regenerate caches rather than transferring them. Regenerating an old PDF requires Browser Run. These local safeguards need staging validation, and SQLite point-in-time recovery retention still needs review.

Export fallback obtains a fresh Vault stub after a cache RPC error, including when an older Vault lacks the cache methods, before checking the session. It does not retry a failed cache write or session check. Upload reservation rechecks the session and refreshes the durable intent after alarm scheduling; the Vault then validates the bytes and canonical key, recomputes the upload digest and rechecks ownership before recording a marker and sending the R2 put. An older Vault without the new RPC cannot receive these uploads through the current Worker; there is no unfenced fallback. The bounded source body now crosses the Vault RPC, so concurrent upload memory and latency need staging load tests. Older deployed writers do not use the new path.

After each paginated R2 sweep, the code checks a fresh first page and retries if any object is visible or the listing is incomplete. This catches some objects missed during a changing listing, but confirms emptiness only at that point in time; an earlier unresolved write can still arrive later.

Maintenance transfer and import check the Vault lifecycle as well as the deployment fence, including after asynchronous hashing and storage reads. Transfer pages consume rows incrementally before applying the page-size limit. An import must receive every content page before it enumerates sources to copy, and current replacement-copy puts are tracked individually; the target cannot close or finish import while one is unresolved. Independent source closure, older unfenced writers and recovery of uncertain puts still need a safe resolution.

After committing deletion and its retry alarm, the Directory now attempts to quiesce both the active Vault and any preparing replacement targets before acknowledging the request. It attempts all targets even if one fails; the alarm retains cleanup work. A target whose initialization is still in flight may not yet be quiesced, and a previously dispatched put can still arrive, so this does not establish erasure or safe migration.

After quiescence, deletion also attempts to cancel already-known billing, delete known Workflow instances and sweep currently visible R2 objects while waiting for close. Retirement also attempts known Workflow cleanup before close. These are preliminary actions: an unresolved fence keeps the account pending, and billing, Workflow termination and the final R2 sweep still run after a successful close. A missing Workflow is checked again on a later attempt and does not settle an uncertain create. The Directory has separate deletion, retirement and finalization lanes, each with up to four concurrent operations; a free slot starts the next item even when another remains unresolved. Four stalled operations still block later items in that lane, the alarm awaits every lane, and a second finalization pass waits for all retirements. A retry alarm is scheduled before external calls; progress depends on its delivery or a runtime reset. A vault indexed as both current and retired remains pending for review, and the final Directory transaction rechecks for a retired vault after external calls. None of this proves that an earlier unknown write or Workflow create cannot arrive later.

Active account deletion checks the Vault's persisted owner before quiescing, reading billing or run data, closing or destroying it. New deletions retain the closed Vault until the delayed final sweep and recheck its owner before that sweep; the Directory records a successful destruction acknowledgement before continuing identity and billing cleanup, so later cleanup failures can retry. Older swept rows have no independent owner proof and remain pending; a lost destroy acknowledgement also remains pending, since an empty Vault does not prove who owned it. A changed mapping after an external cleanup request is dispatched cannot recall that request. Same-owner cross-shard publication, mixed-version behavior, provider retention and complete erasure remain unproven.

Global invitation cleanup now uses a durable inventory barrier for a matching, account-bound grant. The coordinator fences new identity writes, advances the authorization epoch, seals all 16 shards and checks their active-user counts alongside the local Directory inventory. It decides against the bound generation, advances the epoch again, and releases the barrier only after every shard acknowledges closure. Each retry gets a distinct inventory attempt ID, and a shard records a redacted tombstone even if close arrives before seal. A timeout leaves an unknown close pending; a late seal cannot authorize the decision. The inventories reject malformed or oversized data and are capped at 10,000 users per Directory. Active barriers temporarily block account creation and some other identity operations. A target shard seal also blocks writes to its finalization, identity and vault-mapping tables, including unrelated accounts on that shard, so alarm delivery and shard availability affect sign-in, deletion and maintenance. The code counts deleting accounts as no longer retaining a grant because it has no reactivation path; verify restore and mixed-version behavior before enabling it.

**The inventory rollout is disabled by default.** A still-matching invitation needing cross-shard verification remains pending unless `INVITE_INVENTORY_DRAIN_VERIFIED` is explicitly set to `verified-v1` after an independently verified drain of older coordinators and shards. This setting is an operator assertion, not evidence of a drain. SQLite guards reject several older writes after migration but cannot prove that already-dispatched requests or older runtimes have stopped. No such drain or deployed recovery drill has been verified. The opt-in `global-invite-orphan` diagnostic completes deletion while preserving an unindexed shard identity's grant under the local test assertion; it is not proof of deployed safety.

New global-home accounts record the invitation generation, or its known absence, at creation. A later reissue survives deletion even if it occurs between Vault deletion intent and Directory capture. Accounts and receipts predating that binding remain ambiguous: a still-matching invitation is held for operator revocation or reissue. Global removal rechecks the user, vault, deletion operation and final-sweep generation before deciding; delayed requests after a restore or mapping change are rejected. If the finalization changes after the decision, the barrier is released only after all shard closures and the receipt remains pending for reconciliation. New Google shard accounts routed through V3 also bind the normalized email and invitation generation to an opaque creation claim. Before removing a matching grant, the target shard verifies and seals the exact identity, claim, vault, deletion operation and finalization; the coordinator requires that versioned proof. Local tests cover the formerly pending sequence where the global account is erased first and the shard account is deleted last. Older shard accounts without that binding still hold a matching invitation for operator review. A changed Google email on a V3 shard account also fails closed until a reconciliation or change-email path exists. Older deployed code and already-dispatched requests require draining and mixed-version testing.

The new shard protocol retains claim metadata until the associated home is released. Binding a new V3 home rechecks the current invitation in the same transaction, so revocation prevents the delayed account from being bound while invite-only mode is enabled. The target create itself can still arrive after revocation and leave an unbound shard account; an interrupted or abandoned claim can need operator recovery. The current invitation cannot safely backfill a legacy claim because it may be a reissue. Local tests cover lost bind replies, changed claim data and late seal or close messages, but do not establish deployed mixed-version behavior or complete erasure.

The earlier test-only seal prototypes remain as adversarial diagnostics. Current local tests cover cold-shard bootstrap, stale authorization epochs, malformed inventory, late seal responses, lost close acknowledgements and alarm-arm rollback. They do not replace a deployed failure and recovery drill or establish provider retention and complete erasure.
The current retirement protocol checks the persisted owner on each Vault lifecycle call and keeps the Vault closed through the delayed second R2 sweep before destroying its SQLite data. Retired-row generations, timestamp checks and cancelled replacement operations prevent several stale local transitions; prior `swept` rows without ownership proof and lost destroy acknowledgements remain pending. An owner match alone does not prove that another Directory cannot claim the same Vault, and a delayed identity release or initialization cannot be recalled by a later recheck. Mixed-version behavior, same-owner cross-shard publication and old writers remain unproven.

**Identity placement after deletion remains unproven:** after the new migrations activate, a sharded Google deletion advances the global OAuth epoch when releasing its home, records the acknowledgement locally, then raises a persistent shard authorization floor in the same transaction that removes the identity. SQLite guards reject markerless legacy Google inserts and releases. Local tests now reject the two reproduced delayed Google-creation races, including one with a replacement account. Conflicting homes and unbound deletion releases fail closed, and a lost reply can cause another epoch advance and interrupt unrelated sign-ins. These tests do not establish a deployment drain: pre-migration objects and mixed versions can still execute old paths. Abandoned unbound claims, retention and recovery also remain unresolved. The experimental synthetic protocol has a separate diagnostic whose first read carries no pre-deletion authorization; the coordinator cannot distinguish it from a new sign-in. Do not rely on deletion across shard-configuration changes until rollout, recovery and retention are verified.

New Google shard homes now receive an opaque coordinator claim token, recorded with a newly created shard identity in the same transaction. The current Worker uses distinct claim-aware RPCs and checks the target's token before binding an unbound home; matching tokens also let a later sign-in recover an interrupted initial bind. SQLite rejects an older post-migration bind of a tokenized home without the matching transaction marker. A changed claim, missing home, or unbound legacy home without a token remains pending for review. Already-bound legacy accounts remain reachable. Older coordinators lack the new RPC, and an older target cannot record a token, so those mixed-version creation paths fail closed. The token does not register or seal in-flight creation attempts: an older Worker or delayed target call can still leave an orphan, and old code before migration can bypass the guards. Mixed-version draining, orphan recovery and the full registered-attempt protocol remain unresolved. The deletion probe counts user-linked tokens and conservatively treats unbound or orphaned coordinator tokens and unexpected bind markers as incomplete evidence.

A later migration also advances and records a one-time global rollout epoch; a shard installs that floor before serving its first request after upgrade. This addresses a local regression in which a deletion finished before the shard had any floor. First activation depends on the global Directory and fails closed if that lookup fails. Local tests exercise the bootstrap and retry helper, but a deployed outage, migration ordering and mixed-version drain remain unverified; the global epoch advance also invalidates outstanding Google sign-ins.

The current global code rejects legacy Google shard-release RPCs even if the home is already absent, so an old caller cannot treat that no-op as a release acknowledgement from the current implementation. An older global runtime can still return success for an absent home because no SQL delete fires; mixed-version draining remains a release blocker. The Directory deletion probe also counts the user-linked retry and deletion markers and the vault-keyed initialization fence. Neither change makes the Workflow or provider inventory complete.

The Vault deletion probe now counts rows in all visible non-system SQLite tables even if initialization or schema markers are absent. The Directory probe counts all unattributed billing events conservatively against every account, in addition to events attributed to the requested user. Pending events with an empty owner can be reconciled only when Stripe returns the matching customer and an active local account; missing or inactive owners remain pending, although independently customer-linked deletion can remove them. Already-applied unattributed events still need a safe reconciliation procedure. These rows can hold unrelated audits pending, and the probe does not identify events incorrectly attributed to another user, so billing-event coverage remains incomplete. Neither a zero row count nor an empty R2 listing establishes complete erasure.

When the Vault lifecycle schema is missing, close and destroy now stop if any visible application table remains, including an empty table that could indicate a lost Workflow inventory. A genuinely empty uninitialized Vault can still be closed. This safeguard does not enumerate provider instances or identify hidden or in-flight work; incomplete Vaults require operator recovery.

The Vault alarm uses separate bounded lanes for expired-upload cleanup and pending Workflow reconciliation, allowing independent work to progress when one R2 delete or status call stalls. Expired-upload scans persist a wrapping cursor so repeatedly failed or fenced reservations do not starve later candidates across completed alarm invocations. It still awaits all lanes, so four stalled calls in a lane can block later items in that lane and a stalled call can prevent the alarm handler from finishing. A delete already dispatched cannot be recalled on Vault closure. Resume failure reconciliation checks that the observed run is still current before changing it. Workflow absence checks reject a named not-found error if its instance ID differs from the requested ID. This prevents that error from proving a different run absent, but does not establish a complete inventory or settle an uncertain creation.

Saved versions with missing skill provenance or duplicate line IDs remain owner-readable but cannot be exported or shared until reviewed. These checks do not prove that a retained quote still matches its source, or replace a live judge and historical-data compatibility validation.

Historical detached edits and legacy-provenance versions remain available to the owner but are blocked from document rendering, MCP resume delivery and coach sharing; existing share snapshots are checked against their stored resume version before delivery. Stored versions also undergo the current deterministic number, name and scope checks against their captured evidence; an old quote without origin metadata is not sufficient evidence of a user's later correction. They can remove unwanted lines or check them against confirmed facts before finalizing; headings and skills must also be confirmed. Prior versions and issued shares remain unchanged. The Vault now accepts each tailoring checkpoint only at its corresponding step and recomposes a finished resume from the stored verified draft and captured inputs. A changed line, citation, role heading or report cannot be published through the finish patch. It also applies the deterministic export check before committing a finished run, so a checkpoint rejected by that check cannot consume a credit and leave an unexportable ready resume. These checks are heuristic and protect the current publication boundary; they do not prove that an older runtime or a live judge produced a correct verification.

Owners can also remove a line or a skill from an already checked resume. The result is a new version, while earlier versions and existing share snapshots remain unchanged; stale requests and removal during document generation are rejected. The checked version must pass the grounding guard before and after removal. The displayed gap analysis describes the original matching and does not claim that the current resume covers every requirement.

A narrow grounding check rejects direct completed-action wording when the matching source states only an explicit plan. It is actor-insensitive and can conservatively reject implicit completion; passive, compound and indirect plans still require the independent judge.

A deterministic check also catches a narrow percentage swap between two directly stated English outcomes, such as assigning throughput's 30% to latency when the source gives latency as 50%. Passive voice, bounds, qualified phrases and ambiguous occurrences remain for the independent judge; this does not prove numerical entailment.

Grounding also catches a narrow object-specific contradiction such as a denied Kubernetes deployment paired with a separate positive Docker deployment. The check does not resolve the actor and can conservatively reject ambiguous statements; qualified, longer and ambiguous clauses still require the independent judge. It does not establish general entailment.

It can plant cases the deterministic direction check does not recognize, and reports changed wording as uncertain unless it restores a still-cited exact fact. Its three local cases use a stand-in judge and cannot establish live-model recall or a release catch rate.

The current profile editor uses revision-checked saves and keeps an unsaved draft on conflict. A fresh read can reconcile a lost response only when the next revision contains the submitted values. A narrow English direction check rejects some reversed outcomes when the claim and evidence name the same object, such as increased versus reduced latency. It skips several ambiguous qualifiers and negative contexts. It can miss different wording, longer objects, context-dependent changes and other languages; it does not establish semantic entailment or replace a real-model judge.

The deterministic number check distinguishes common explicit date contexts from counts, so a year in a dated range cannot by itself support an employee count with the same digits. It binds recognizable date components together without guessing the order of ambiguous numeric dates. It checks common English scaled quantities such as “one hundred and 5” and ranges such as “5 to 10”, including several line-wrapped forms, as units; it preserves several bounds and approximations and blocks several unparsed fraction, malformed-number and numeral forms rather than treating their components as evidence. More than 128 consecutive horizontal whitespace characters, or excessive accumulated spacing, make the entire input unmatchable for numeric claims. This limits a measured slow path at the cost of rejecting some valid claims; other pathological inputs have not been ruled out. These checks can reject valid representations, such as “half a million” for 500,000, decimal commas or the same range written differently. Unrecognized or differently wrapped ranges can still be split into independently matchable components; plain 19xx–20xx ranges retain the existing year interpretation. Other number words, languages and semantic context remain incompletely covered. These heuristics do not prove numerical entailment; fix and evaluate the remaining cases and measure precision and recall on real cases before release.

The number check also distinguishes several negated English comparisons such as “not more than” from the opposite bound. A separate action check rejects some contradictions between an action and its explicit negation. Both are narrow heuristics: other phrasing, languages, distant negation, multiple subjects and simultaneous positive and negative assertions remain uncertain and require the independent judge and real-data evaluation.

Role attribution uses the nearest verified header and leaves conflicting or ambiguous assignments unattached. This check cannot establish reading order after a poor conversion or detect every missing, unmarked header; evaluate role assignment on real layouts before promotion. Date parsing clears dates when multiple ranges share a converted line, including an ended and a current role with the same start year. This can omit valid dates and cannot detect every ambiguous line with only one range.
